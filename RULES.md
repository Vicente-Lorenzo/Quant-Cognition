# Quant Trading Framework Project Guidelines

## PROJECT OVERVIEW
A **multi-purpose Quant Trading Framework** built around **cTrader**.
- **Root Folder:** `cAlgo` (located in Documents for cTrader compatibility).
- **`Library/` (Python):** Core logic, AI models, trading systems, persistence, and the Dash frontend.
- **`Sources/` (C#):** cTrader Robots, Indicators, and Plugins bridging to Python via shared memory (named `mmap` + auto-reset Event signaling, single-slot request/response lockstep).
- **`Tests/` (Python):** Pytest suite mirroring the `Library/` layout.
- **`Setup/` (Python):** Zero-to-hero provisioning (`Setup/Install.py`) and the registrar for the three standard Scheduler workflows (`Setup` · `Environment` · `Market`).
- **`Research/` (Python):** Frozen research method + tooling per campaign (see the `Research/` section below).

## OPERATIONAL TRAPS (each of these has cost hours)

- **Learning CLI:** `--timeframe Hour` / `Daily` — the *friendly* parameter-tree key, never `H1`/`D1`. A missing key **auto-vivifies an empty node** and fails silently.
- **Learning verbosity:** never run H1/large-bar Learning at `Info`/`Debug` — per-bar log flood costs ~0.6s/bar (a 9h hang for one episode). Use `Warning` always; spawn workers too.
- **`LearningAPI._export_`** has a signature collision — run with `export=False`.
- **Logging:** silence via sink levels (`log.console.set_level(...)` / `log.file.set_level(...)`), never stdlib `logging.disable()` — the fast path bypasses stdlib entirely. `VerboseLevel` is ordered by **verbosity**, so `Debug` is the largest value and a sink accepts `record <= sink`; this is the inverse of stdlib.
- **Console encoding:** `·`/`→` crash cp1252 stdout — use `conda run --no-capture-output` and/or `PYTHONIOENCODING=utf-8`, and `sys.stdout.reconfigure(encoding="utf-8")` in standalone scripts.
- **`QueryAPI` placeholders:** raw SQL cannot use `::type` casts — `::name::` is the interpolation token. Use `CAST(x AS text)` / `to_char(...)`.
- **BLAS in standalone scripts:** calling `np.corrcoef`/LAPACK without importing `Library` first can abort the process (exit 127) — set `KMP_DUPLICATE_LIB_OK=TRUE` or import `Library` to get the `libiomp5md` preload.
- **ProcessPool cleanup:** kill worker **children before parents**; orphaned `spawn_main` workers hold ~2 GB each at 0% CPU forever and starve later runs.
- **`psutil` cmdline filters** match your own `python -c "...script.py..."` probe — exclude `os.getpid()`.
- **This repo lives under OneDrive** — `shutil.rmtree(..., ignore_errors=True)` can fail silently on sync-locked paths; pass an `onerror` handler and verify with `path.exists()`.

## CODING PHILOSOPHY
1. **Precision & Accuracy:** Prioritize correct, working code over speed.
2. **Simplicity & Optimization:** Do not over-engineer. Solutions should be as simple, concise, readable, and performant as possible.
3. **Measure, Don't Guess:** Profile before optimizing (`cProfile` by cumulative + tottime, targeted micro-benchmarks). Validate bottleneck hypotheses with data.
4. **No Environment Configuration:** No `QUANT_*` (or other) environment variables — behavior is controlled exclusively through constructor arguments and CLI flags.

## RESPONSE STYLE
Lead with the conclusion, prefer **bullet points and tables** over prose, and omit filler. Reserve long-form paragraphs for when they are explicitly requested.

## CODING STYLE & ORGANIZATION
1. **Language:** All written content uses **English (US)** spelling (`Optimization`, `behavior`). The only exception is identifiers mirroring an external API verbatim (e.g., cTrader's `Cancelled`).
2. **General:** No docstrings or comments. Tidy files (no trailing spaces), one blank line after `class` and between methods. (Exceptions kept by explicit request: paper-mapping docstrings in `Library/Model/Method/DDPG|SAC|TD3`, API-surface docstrings in `Library/Bloomberg`, `Library/Database` and `Library/Logging`. Do not strip these.)
3. **Naming:** `CamelCase` for public members; `_naming_` for private ones; `UPPER_SNAKE` for public constants and `_UPPER_` for private class constants. Lowercase `__post_init__` arguments.
4. **Typing:** `Self` from `typing_extensions` for instance returns (Python 3.10 compatibility). `from __future__ import annotations` first line only when forward references require it. Prefer built-in types over `typing` classes.
5. **Imports:** Sorted ladder-style block; one blank line between external and project (`Library.*`) imports; explicit imports for internal modules. Package `__init__.py` re-exports follow logical order from least to most important (foundational models first, the flagship API last). Always import `np`/`pd`/`pl` from `Library.Database.Dataframe` (never directly) so the shared display configuration applies — the only exceptions are `Dataframe.py` and its import closure (`Database.Dataclass`, `Utility.Typing`).
6. **Density:** Dense method bodies without internal blank lines (except complex `__init__`); standard spacing in signatures and assignments.
7. **Architecture:** Order methods by category (Connection → Disconnection → Business) then by complexity (simplest first); fields, properties, and methods follow logical order from least to most important. `@staticmethod` for stateless logic, `InitVar` for temporary inputs. Shared helpers live in `Library/Utility` — promote repeated logic there instead of duplicating it.
8. **Dataframes:** Capitalize framework-level columns (`Date`, `Security`). Prefer Polars (`pl`) for performance; Pandas (`pd`) for compatibility.

## LOGGING CONVENTIONS
Logs must be short, objective, informative, and visually distinctive.
1. **Message Format:** `<Category> Operation: <Outcome> (<primary detail>)`; join extra fields with ` · ` (e.g., `Phase Warmup: Completed · 1.20s · 205 Ticks · 41 Bars`).
2. **State Transitions:** `[StateA] → (Reason) → [StateB]`; `→` is reserved for transitions. True state changes log at `Info`, self-loops at `Debug`, hot-path self-loops keep `reason=None` (silent).
3. **No Commas or Periods:** Use ` · ` in place of `,`; one sentence per message with `:`, ` · `, parentheses, and symbols; no end-of-sentence periods.
4. **Debug vs Info:** `Info` is strictly trading/execution and periodic trader-useful information; `Debug` is everything else (connections, per-query execution, warmup internals).
5. **Errors & Exceptions:** `<Category> Operation: Failed · <Reason>` with the reason capitalized (e.g., `Connect Operation: Failed · Due to port being in use`).
6. **Tags:** `Class` and `Subclass` are **derived automatically** from the calling context — do not pass them. `Class` resolves to the owning object (`type(self).__name__`), falling back to the module; `Subclass` resolves to the subsystem (`Library/System/Realtime.py` → `System`, `Setup/Auth.py` → `Setup`), falling back to the parent folder under `python -m` or direct script execution. Pass either only to **override** a derived value with something the frame cannot know (a database name, a runtime label); pass `Subclass=""` to drop it and `identify=False` to drop both. Reading order is always **specific → subsystem** (`ExecutorAPI - Scheduler`), never the reverse. Run identity that spans the whole process (provider · ticker · timeframe) belongs in `LoggingAPI.set_class_tags(...)`, which renders *before* the level.
7. **Capitalization:** Title Case for fixed labels and nouns (`Bars`, `Ticks`); capitalize the leading word of free-text reasons.
8. **Verbose Levels:** Entry points (main functions) set the two primary sinks explicitly and symmetrically through a logger instance — `log.console.set_level(...)` and `log.file.set_level(...)` — never through the class: Console drops to `Info` when `Debug` is too verbose · File is always declared `Debug` even though that is its default. Sinks are process-wide, so the outermost `with log:` locks them and a nested script cannot override. Use `with log.console.temporary(...)` for a scoped change; it restores the previous level, not the default.
9. **Lazy Messages:** Pass a `lambda`, never an already-built string — `log.debug(lambda: f"...")`. A record no sink accepts then costs ~128 ns instead of rendering an f-string, a dataframe or a repr that is thrown away. Capture loop or `except` variables with default arguments (`lambda error=error: ...`) so the closure holds the value at creation time. Bare constants (`log.info("Started")`) are fine — there is nothing to build.

- **`Library/Scheduler`**: DB-backed job orchestration on the Postgres `Scheduler` schema; replaces Windows Task Scheduler with a single boot daemon. **Model:** one shared `Kind` enum ∈ {`Manual`, `Scheduled`, `Service`} spans the module — on a Workflow it is the lifecycle (`Manual` = run on demand, no cron · `Scheduled` = cron opens cycles, `Schedule` required · `Service` = one **resident** cycle, only `Service` members allowed), on a Task the execution style (`Manual` standalone on-demand · `Scheduled` run-to-completion · `Service` always-on), on a Cycle/Run **how that execution was triggered** (daemon = `Scheduled`, human = `Manual`, supervision = `Service`). `WorkflowAPI` (`Waits` default true governs overruns) → `CycleAPI` (**one execution of a workflow** — the Airflow-DagRun analog: `Kind` · `Status` · `StartedAt`/`StoppedAt`; opened by the workflow cron at its logical instant, by `run_workflow`, or by boot) → `TaskAPI` (`Type` ∈ {`Batch`, `Shell`, `Python`} · `Kind` · optional `RequiresApproval`/`RequiresReview` gates · `MaxRetry`/`RetryDelay` · `Waits` (default true)/`Tolerates` (default true)) → `RunAPI` (audit record: kind, status, exit code, 0-based `Retry`, duration, peak memory, `PID`, `Auditor`, captured log; per-run `MachineAPI`; status groups `Busy` ⊂ `Live` ⊂ `Active` — `Busy` = Waiting·Running (a process holds a heartbeat: budget, reaper) · `Live` = +Retrying (work in motion: cancellable, pauses services) · `Active` = +Approving·Reviewing (unfinished: blocks the DAG, dedups, keeps the cycle open)); `DependencyAPI` holds the DAG edges, cycle-checked and evaluated by `CoordinatorAPI` (networkx). **Semantics:** ONLY the workflow `Schedule` (or a manual run) opens a Cycle; a member task's `Schedule` is an **earliest-start gate inside the cycle** (never a trigger; `Manual` cycles ignore gates); a member fires when its gate time passed AND its dependency rule holds — `Waits=true` waits for predecessors (`Tolerates=true` accepts any terminal outcome · `false` demands `Success`), `Waits=false` fires at its gate time (blocked only by an already-`Failure` predecessor when `Tolerates=false`). `ManagerAPI` **validates coherence** — Kind vs Schedule, Service-workflow purity, and member schedules fitting inside every workflow period (`CoordinatorAPI.fits`). The cycle stays open while members are active, dispatchable, or gated in the future; it closes `Success`/`Failure` and mirrors member gates as `Approving`/`Reviewing`. **Overrun:** the next cron occurrence waits for the open cycle when `Workflow.Waits` (default) · `Waits=false` **resets** — kills the open cycle's live runs (`Failure`) and opens fresh. **Overrides (all stamp `Run.Kind=Manual` + `Auditor`):** `run_task` early-starts a member into the open cycle ignoring its gate; `skip` inserts a synthetic run without executing; `cancel` tree-kills a live run via its `PID` — skip and cancel **simulate a termination with a chosen result** (default Success · `--failure`) that flows through the gates (`RequiresApproval` → `Approving`, `RequiresReview` → `Reviewing`). Approval gates a passing run and Review gates a crashed one (Accept → `Success`, Reject → `Failure`; gates block downstream); crashes retry up to `MaxRetry` with latest-attempt-governs; a heartbeat lease lets the reaper recover dead runners/reboots; `Service` tasks are supervised always-on, suspended while a workflow-mate `Scheduled` run is **executing** (`Waiting`/`Running`/`Retrying` — a gate-parked `Approving`/`Reviewing` run does not hold services down), respawned no sooner than `RetryDelay`, and halted after `MaxRetry` consecutive short-lived crashes (**0 = respawn forever, the service default**, systemd-style). `Run.PID` records the run's root Runner process — the tree that `cancel` and reset kill. **Boot sequence:** at daemon start every enabled service-bearing workflow is boot-launched as a fresh maintenance run, and a down `Service` only spawns once its DAG predecessors are satisfied (`Scheduled` predecessor = a run finished since this daemon start · `Service` predecessor = alive process) — so a reboot replays `Update → Tunnel → Server` strictly in order. **Processes:** `SchedulerAPI` is event-driven — Postgres `LISTEN/NOTIFY` triggers (created by `Setup/Scheduler.py`: any Workflow/Task/Dependency change · Run inserts/deletes · Run **status** changes only, so heartbeats stay silent) wake the daemon instantly, with the `interval` (30s default; `interval`/`concurrency` constructor params — zero environment variables) as the cron/fallback cadence; it spawns one `Runner` process per run (never threads, `CREATE_NO_WINDOW` so tasks never open consoles); `ExecutorAPI` executes the artifact (psutil peak-RSS sampling, heartbeats, per-run log file under the system temp `%TEMP%/Quant/Runs`). **Surfaces:** `ManagerAPI` is the single mutation authority shared by the Python console, the CLI (`python -m Library.Scheduler.Main <workflow|task|cycle|run|serve> <action>`), and the web UI; push wake-ups ride the generic `DatabaseAPI.listen`/`notify`/`wait` seam (native on Postgres, sleep-degraded elsewhere); `Serve.py` is the headless boot entry; `Tray.py` wraps it as the silent system-tray app named `Scheduler` (Open in Terminal — Windows Terminal live-tail of `Logs/Scheduler.log` · Verbose Logging toggle · Launch/Shutdown in-process · Restart relaunches the boot script so code changes apply · Quit, headless fallback) — it knows nothing about the web app (`Library/Web` has its own `Quant Cognition` tray; the only sanctioned coupling is the web Scheduler page consuming `ManagerAPI` like the CLI does). Libraries: `croniter` · `psutil` · `networkx` · stdlib `subprocess`.

### Setup (`Setup/`)
- **One boot entry.** Windows Task Scheduler runs only the master orchestrator (`Quant Scheduler` logon task → `pythonw Scripts/Scheduler.py` → silent tray daemon). The daemon boot-launches the service-bearing workflows (a logon replays `Environment.Cache → Retention → Update → Tunnel → Server` in order), supervises services, cron-launches scheduled workflows, and advances manual ones.
- **Three standard workflows** (registered by `Setup/Install.py`, owned by the real administrator `Setup.Auth.ADMIN`): **`Setup`** (manual) = the FK-ordered provisioning DAG (`Enums` · `Auth`→`Logging`→`Scheduler` · `Universe`→`Market`/`Portfolio` · `Indicator`, all `Tolerates=false` — provisioning is zero-tolerance; `Logging` precedes `Scheduler` because `Run.LID` references `Logging.Log`); **`Environment`** (daily `0 4 * * *`) = `Environment.Cache` (bytecode/tooling/build cache cleanup) → `Environment.Retention` (prunes expired log files from the temp folders and expired `Logging.Log` rows) → `Environment.Update` (conda env refresh — suspends the services) → `Environment.Tunnel` (cloudflared, `Service`) → `Environment.Server` (waitress app, `Service`); **`Market`** (daily `0 6 * * *`) = `Market.Calendar` (Forex Factory economic calendar), extensible.
- **Provisioning tasks** are idempotent Python modules with a uniform `main(database="Quant") -> int` and RULES logging — re-run any task or the whole DAG safely; each also runs standalone (`python -m Setup.Auth`, …).
- **Entry point:** `python -m Setup.Install [--database] [--boot]` provisions everything in-process, registers the three workflows, and with `--boot` creates the Windows logon task. `Scripts/` holds only the essentials: the boot launcher (`Scheduler.py`) plus the environment helpers (`System`/`Conda`/`UV` updaters and the `Cache` cleanup each updater runs first).
