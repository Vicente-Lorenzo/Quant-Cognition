# Quant Trading Framework Project Guidelines

## PROJECT OVERVIEW
A **multi-purpose Quant Trading Framework** built around **cTrader**.
- **Root Folder:** `cAlgo` (in Documents for cTrader compatibility).
- **`Library/` (Python):** Core logic, AI models, trading systems, persistence, Dash frontend.
- **`Sources/` (C#):** cTrader Robots, Indicators, Plugins — bridged to Python via shared memory (named `mmap` + auto-reset Event, single-slot request/response lockstep).
- **`Tests/` (Python):** Pytest suite mirroring `Library/`.
- **`Script/` (Python):** Every script — the boot launcher, the installer and registrar, the Python environment updaters, and one folder per Scheduler workflow (`Setup/` · `Environment/` · `Market/`).
- **`CAMPAIGNS.md`:** the record of the delivered DRL campaigns — setup, agent, features, reward, evaluation methods, results, dead ends and what the next campaign must do. The `Research/` folder that held them was deleted on 2026-09-25.

- **`net.csv` had four defects, all fixed 2026-09-11, all from one place.** `generate_net_report` concatenated the trades and positions frames on `list(set(...).intersection(...))`, which (a) dropped `Position` — absent on `PositionAPI` — so `aggregate_items` returned its input unchanged and **the entire Aggregated half silently became a copy of Individual whenever a position was open** (85 of 85 rows on golden 1); (b) dropped `ExitTimestamp`, so holding time collapsed to `stop - entry` (avg 181.64 days for an H1 year); (c) ordered columns non-deterministically. And `initial_balance` was `account.Balance`, the **closing** balance, so every balance-relative percentage divided by the wrong number — `Max Balance Drawdown (%)` read 44.24 where `absolute / peak balance` gives cTrader's 31.64. - **`net.csv` reads every equity row from its own column's curve — 2026-09-17.** `PortfolioAPI` keeps three `CurveAPI`s — `EquityCurve` · `BuyEquityCurve` · `SellEquityCurve`, a side being the opening balance plus that side's closed and open P&L, so Buy + Sell − opening balance = Total at every bar. Each records one value and three intrabar points per bar and computes nothing until read: a read mid-session catches up only what is new, and the result is **bit-identical however it was read** (one vectorised pass at the end, random reads, a read every bar — sums use sequential `np.add.accumulate`, never a pairwise sum). Curve rows: Net/Upside/Downside Volatility (per bar and × √bars per year), Max/Mean Equity Drawdown/Runup (intrabar), `Risk-free Rate (%)`, and every ratio twice — Sharpe and Sortino per bar and annualized, Calmar and Sterling over the whole period and annualized, the risk-free rate deducted in every column. Trade rows (returns, winning/losing, trade volatility, balance drawdown, streaks) stay trade-based and follow **realization order** — exit time, never entry time: 676 partial closes share an entry stamp on the DDPG golden, and shuffling those ties moved Max Balance Drawdown from 20.66 % to 26.69 %. `FitnessType` names and values did not move (`SharpeRatio` is still "Sharpe Ratio Annualized"); the constants are `SHARPERATIO` per bar and `SHARPERATIOANN` annualized. `update_data` went from 20.1 to 12.3 µs with two positions open, three curves included, and the report-time catch-up is about 12 ms per curve per 60k bars. `calculate_statistics()` defaults to the recorded window, so the full report is available mid-session.
- **Epoch conversion: two pairs, and they must agree.** `datetime_to_epoch`/`epoch_to_datetime` are pure arithmetic against a naive `EPOCH` and were always timezone-neutral — `BacktestingAPI` uses them, which is why the offline goldens never moved. `datetime_to_timestamp`/`timestamp_to_datetime` used `.timestamp()`/`.fromtimestamp()` and were therefore **local-dependent**, so `RealtimeAPI` stored cTrader's UTC wire stamps as naive **local** time, off by the UTC offset and shifting across DST. Fixed 2026-09-11: the epoch is always read as UTC and a new `zone` argument only decides the label — `None` gives **naive UTC**, a zone gives an aware datetime. `utc_now(zone=None)` is now the single source of "now". **Everything in the framework is naive UTC unless a boundary explicitly asks for a zone.** Do not reintroduce a second convention.
- **Stored stamps are naive UTC too, and cron is the one exception — deliberately.** 2026-09-15: the 32 remaining local `datetime.now()` calls (every `UpdatedAt`, Scheduler `StartedAt`/`StoppedAt`/`Heartbeat`, `Logging.Log`, `Session` timestamps, run-folder names) became `utc_now()`, and `LoggerAPI.stamp` renders UTC so a log line matches the row it describes. **A cron expression still means wall-clock local time** — `0 4 * * *` fires at 04:00 local in both BST and GMT — so `SchedulerAPI._due_`/`_timely_` and the cycle start convert with `utc_to_local` before `croniter` and `local_to_utc` after; `CoordinatorAPI.fits` anchors on `local_now()`. **The repeated hour when clocks go back is handled explicitly:** `_next_` keeps advancing croniter until the UTC candidate is strictly later than the last firing, `_previous_` tries both readings of the hour, `utc_to_local` sets `fold=1` when the round trip disagrees, and `_advance_` never starts a cycle before now — a 01:30 schedule fires once on that night, a sub-hourly one skips the repeated hour. Before this, a `30 1 * * *` workflow in `Europe/London` would have opened a new cycle every tick for a day. Those three helpers live in `Utility/Datetime` and rely on the OS DST rules, so a naive value converts correctly for **its own** date. `Script/Setup/Timezone.py` migrates rows written under the old convention (dry-run by default, `--apply` once, marker under `inspect_persistent("Migrations")`); it skipped the old `Market.Tick`/`Market.Bar`, believing them broker-side UTC — they were Europe/London local, and the Phase 3 switch replaced both with a UTC tape. **The daemon and the executor must be restarted together** — a mixed pair reaps healthy runs or stops reaping stale ones for the offset.
- **Zones are chosen, never assumed — one for display, one per workflow.** 2026-09-16. **Display:** the server always sends UTC; every rendered stamp carries it (`data-utc` on detail spans via `StatusAPI._stamp_`, and `Lightweight.js` marks table cells matching `YYYY-MM-DD HH:MM:SS`), and `App/V2/Assets/Scripts/Zone.js` formats them in the zone picked under Settings → Appearance (`GLOBAL_ZONE_STORAGE_ID`, per device, default **Browser**). Charts follow the same zone — `Lightweight.js` formats the crosshair, axis labels and range dates through `AppZone.epoch` and re-applies them when the zone changes, so a result page never shows two zones (tick marks still sit on UTC boundaries; only their labels move). Zone.js watches text and `data-utc` attribute changes as well as inserted nodes, because React updates a polled detail span in place. Nothing in a payload changes, so old run artifacts render in the chosen zone too; CSV exports, the sheet PNG and a standalone `Plot.html` stay UTC. **Cron:** `Scheduler.Workflow.Zone` (IANA name, empty = this PC's zone) is the zone the workflow's cron is written in — `_due_`, `_timely_` and the cycle start pass it to `utc_to_local`/`local_to_utc`, so `0 9 * * 1-5` in `America/New_York` follows New York's own daylight saving. Member task schedules use their workflow's zone; a standalone scheduled task uses this PC's. `ManagerAPI._zoned_` refuses an unknown name.
- **A suspended daemon must not reap on wake.** 2026-09-16: Windows slept 09:53 → 15:49 UTC, the daemon's first tick found six-hour-old heartbeats and reaped the live Server and Tunnel runs as `Failure` while both kept running. `SchedulerAPI._suspended_` treats a gap of more than **two intervals** (constructor arguments, 30 s interval, 90 s lease) between its own successful ticks as time it could not observe and defers reaping for one more lease, long enough for every live executor (15 s heartbeat) to beat again. **A database outage is the same case — 2026-09-27:** a Postgres backend crashed at 04:30:38 UTC (access violation in `postgres.exe`, offset `0x509b76`, under 28 backfill workers; the postmaster reset and replayed WAL in 92 s), heartbeats could not be written for longer than the lease, and the daemon's first tick after recovery reaped the four live services, whose next heartbeats set them back to `Running` beside a `StoppedAt`. The threshold was `interval + lease` until then, which a 92 s outage never reached. **A runner whose run was closed elsewhere stands down:** its heartbeat updates only a row with no `StoppedAt` and, finding none, stops its child and leaves the row as the closer wrote it — so a reaped runner never runs beside the replacement the daemon starts. **Latest-row queries order `"StartedAt" DESC NULLS LAST`** — Postgres sorts NULLs first, so two stale NULL-stamped rows made `_suspend_` see a finished run and skip closing the live one.
- **One numeric tolerance: `Utility/Math.EPSILON` = `1e-8`, the default `tolerance` argument of both `equals` and `truncate`.** Unified 2026-09-15 from four values (`EPSILON` 1e-8, `TOLERANCE` 1e-6 in `truncate`, 1e-12 in `equals`, `BacktestingAPI._EPSILON_` 1e-9), measured first: across the five offline goldens, 7 463 `truncate` calls give identical cents at 1e-6, 1e-8, 1e-12 or 0, and 5 412 `equals` calls give identical answers. **The truncation reproduced cTrader's backtester's cent quantisation, not the tolerance** — commission has been rounded half up per deal like the live broker since 2026-09-29 (`quantize`, the same tolerance) (0.045 → 0.04 on golden 2). The tolerance is still a real guard: 1 127 commission values land within 1e-14 of a cent boundary, all from above in these runs, and one from below would lose a cent without it. `equals` is relative with a floor of 1 — `abs(a - b) <= tolerance * max(1, |a|, |b|)`. **Do not change `EPSILON`'s value:** DDPG standardisation adds it to the variance, so it is an input to the thesis model. The SAC actor's own 1e-6 is a paper constant, not a tolerance.
- **Decompose by direction before believing an aggregate.** Twice in one session an aggregate gap read as a per-trade residual and was neither: the gross gap was one open position, and the balance-drawdown gap looked like a partial-close effect until run 4 (which has partial closes) matched. Long/short and absolute/percentage splits both collapsed a hypothesis that a total alone supported.
- **The tick tape — `Market.Tick`, the only market table since 2026-09-25.** `UID` bigint (`security << 42 | UTC epoch ms`, primary and partition key — it *is* the time) · `Security` integer (foreign key to `Universe.Security`, compression segment-by) · `Ask`, `Bid` bigint **not null**, price × 100 000 (the Open API's unit for every symbol; a price must divide by it exactly — measured: a finer scale such as 10^8 costs 70 % more space) · `Volume` double, **null unless a provider reports sizes** · `UpdatedAt`, `UpdatedBy` (provenance: `Market`, the service that wrote the row). A hypertable in 31-day chunks (one per security-month), compressed segment-by `Security` order-by `UID`, statistics 1000 on both keys. **1 663 014 876 ticks in 7.0 GB, 4.45 bytes a tick**; the whole database 7.2 GB, from 365 GB. `TapeAPI` (`Library/Market/Tape.py`) owns it: `create` (the DDL), `read`, `first`, `securities` (from chunk metadata: 0.13 s where an `EXISTS` per security took 11 s on the compressed table). `first` costs about 190 ms whatever the query (`MIN` or an ordered `LIMIT 1`: planning over a thousand chunks), so `before` asks for it only when a read comes back short. **Read it one binary blob per chunk and decode in parallel, never row by row:** every row-wise path, `COPY` included, stalls near 1.3 M rows a second on the GIL; `read` spreads the chunks over at most 32 sibling connections (`DatabaseAPI.sibling`, `DatabaseAPI.binary` — generic, each driver supplying the cursor that returns a blob as raw bytes: Postgres the binary protocol, Oracle a `BLOB` fetched as `LONG_RAW`, SQL Server's default) and decodes each into preallocated arrays in threads — measured 2026-09-25 on EURUSD: eleven years (221 M ticks) in 4.4-4.8 s at 32 connections, 5.0 s at 24, 5.5 s at 16 and 83 s on one; a year in 0.8 s, a month in 0.35 s, a dense day in 0.04 s. The old row table read 1.3 M rows a second whatever the connections (eleven years ≈ 166 s). Writing: binary `COPY`, 1.1 M rows a second on one connection; **a new chunk's creation locks the hypertable until the inserting transaction commits, and `compress_chunk` blocks inserts** — both serialised the parallel load that built this table until chunks were created up front and compressed in a second pass. **Name the chunks a statement touches — 2026-09-28.** A `DELETE` through the hypertable locks every chunk and index of every security (7 528 relations, 5.7-8 s on an empty day, whatever the plan), and a scan bounded only by the security's first `UID` locks all of that security's chunks (547 on EURUSD, 14 ms warm, 650 ms cold); compressed chunks all live in one internal hypertable, so either waits on any `compress_chunk` anywhere — the refill's monthly compressions stalled every live poll for about 19 s at a time. `write` therefore deletes from the chunks covering the day (`timescaledb_information.chunks`, 4 locks, 0.4 ms) and `previous` looks back one hour before it scans the whole history (7 locks, 0.6 ms); an upsert touches 8. Check a new statement with `SELECT count(*) FROM pg_locks WHERE pid = pg_backend_pid()` inside its transaction — **and check it past its tenth execution on one connection**: psycopg prepares a statement at its fifth, and Postgres may then switch it to a generic plan, which cannot exclude chunks while planning. Measured 2026-09-28 on the previous-tick lookup: 1 ms and 7 locks for ten executions, then 17.6 s and 16 329 locks on the eleventh — every long-lived service connection had degraded that way, about 23 lookups were running at any moment and the repair crawled at 600 requests a minute. **Every Postgres session therefore runs `plan_cache_mode=force_custom_plan`** (`PostgresDatabaseAPI._driver_`): 1 ms and 7 locks on every execution.
- **Bars are built on demand from the tape, never stored — verified against the platform 2026-09-25.** `TapeAPI.bars(timeframe)` buckets on one clock for every timeframe: **New York time plus seven hours**, so the session day starts at 17:00 New York — H4 opens at 22, 02, 06 … UTC in New York winter and 21, 01, 05 … in summer, D1 at 17:00 New York, W1 on Sunday 17:00, MN1 at 17:00 on the last day of the month before; H1 and below coincide with UTC. A bar is labelled by its own open in UTC. Against the Open API's trendbars on EURUSD: **labels equal on every bar at M1, H1, H4, H12, D1, W1 and MN1 (2016 and 2020-2025), OHLC exact at M1 to D1**, volume off by one or two on about 10 % of D1 bars. The platform's own W1 and MN1 disagree with its own D1 and H1 in 2020 (week of 2020-01-05: W1 volume 456 878, its D1 sum 373 228) and agree in 2024; ours equal its D1, so the difference is named, never copied. No Friday stub bars appear on either side in three years of D1. **Extremes are two-sided:** `HighPoint.AskTick` is the tick at which the ask was highest, `HighPoint.BidTick` the one at which the bid was and `HighPoint.MidTick` the one at which ask + bid was (since 2026-09-28), each at its first occurrence — on EURUSD 2023 the highest mid falls on neither side's extreme tick in 4.8 % of M1 bars, 8.1 % of H1 and 9.3 % of D1, where `(HighAsk + HighBid) / 2` overstates it by up to 1.5 pips, so a mid extreme is never derived from the two sides; `GapPoint` is the previous bar's close. **Volume:** the platform's bar volume is bid updates plus ask updates (exact on every hour sampled, 2020 and 2024), so a tick without a stored size is worth the sides that moved, 1 or 2, and the bar's volume, the sum, equals the platform's; in 2016 the platform counted bid updates only. The build runs in threads, and each extreme is found by one `argmax` per bar where bars average 1 024 ticks or more and by one pass over the whole array below that — eleven years of EURUSD, measured 2026-09-25: D1 0.75 s against 4.6 s by the array pass, H4 1.3 against 4.7, H1 2.4 against 4.4, M15 and M1 tied at 4.3-5.3 s (per-bar calls on M1 would take 52 s).
- **Currency conversion is rebuilt at run time, for any account currency.** cTrader's rule, read from the cBot and reproduced exactly: from asset X to account A, 1 when X is A; a pair X/A's ask and bid; a pair A/X's 1/bid and 1/ask; **never through a third currency unless the run asks** — without `--bridge` the run is refused naming the missing pair, because cTrader's own fallback of 1.0 is a plausible-looking wrong number; `--bridge B` converts X → B → A through two direct pairs, multiplied at every stamp either moves (`TapeAPI.compose`, `TapeAPI.legs`; JPY → CHF through USD agrees with CHFJPY to 6e-5), recorded in the command, the scope and every worker payload. Timing: the direct pair's latest quote at or before the traded tick's millisecond (`TapeAPI.rates`); the residual is same-millisecond ties only. The pair's tape is read once with the run's own, in parallel, and held in memory: bar rows get their rates vectorised at load, a fill looks its rate up by binary search, and the rates at every swap roll are looked up once per run — never a query during the run. The 28 pairs of the eight majors give every account in any of them a direct pair to every asset of every pair: **224 pair × account combinations agree with an independent USD cross to within 1.6e-4, spread level** (a gated test). **Nothing in it is forex-specific:** conversion, sizing, commission and swap key on the ticker's `BaseAsset` and `QuoteAsset` and the contract's terms, so a metal, an index or a crypto instrument prices the same way once it and its conversion pairs are tracked on the tape. **The base conversion is optional — 2026-09-28:** an index's base (`US 500`) has no pair, so a missing base route becomes an empty source (every rate NaN) unless the commission is charged on the base (`BaseAsset…` modes under `Accurate`), which still refuses the run by name; notional sizing then refuses at the first entry (`calculate_conversion_rate`).
- **Swap is charged at the contract's own schedule, in UTC — 2026-09-29.** `ContractAPI.rolls(start, stop)` reads every swap term the Open API sends: `SwapTime` is minutes after 00:00 **UTC**, fixed all year (the Open API's own definition; 1259 is 20:59 UTC in winter as in summer — reading it as 16:59 New York put every winter roll an hour late, and the golden positions closed at 21:00 UTC in winter proved cTrader's), `SwapPeriod` hours between charges, `SwapExtraDay` the tripled day, `SwapWeekends` whether Saturday and Sunday charge, and `SwapSkip` (`skipSWAPPeriods`) the charges a position is spared after it opens; a contract without `SwapTime` charges no swap. `ContractAPI.swap` prices one charge in the quote currency for `Pips`, `Points` and `Percentage` (annual, over 365 days — unverified, no Spotware symbol uses it). **Each night's charge is rounded half up to the cent** (cTrader's rule: Golden 4's positions exact to the cent 347 → 400 of 441, Golden 5's 100 → 114 of 121; truncating was worse). The engine charges every open position at each roll through `PortfolioAPI.charge`, a close takes its volume's share, and a roll inside a bar splits the portfolio's segment there. **cTrader's backtester splits swap wrongly on a partial close**: the closed part takes the *remaining* fraction of the accumulated swap and the remainder keeps it too (a 5-lot US500 position closing 3 lots booked 2 × 2/5 of the swap), so its trades do not add up to the swap charged; the engine keeps the pro-rata split, and that difference is the swap left against cTrader (Golden 4 −8.91 of −1 952). **`ConversionFee`** (`pnlConversionFeeRate`, percent of a realised gross profit, charged when the quote is not the account's asset) joins the commission of every such trade; it is 0 on all 830 Spotware symbols, as `SwapSkip` is.
- **`CommissionType.Units` and `CommissionType.Lots` are flat amounts in the account currency per unit and per standard lot of volume, per side — 2026-09-29** (the order is `Points` · `Percentage` · `Amount` · `Units` · `Lots` · `Accurate` · `Auto`; runs pass the name, so the numbers are free to move). `--commission-type Lots --commission-value 3.5` charges 3.5 USD a lot a side on a USD account whatever the pair, which is what a raw-spread account quotes; `Points` is a price distance in the quote currency, so 3.5 points is 3.5 USD on EURUSD but about 2.3 on USDJPY and 4.3 on USDCHF. It is the thesis campaign's cost model. **Every export also writes `equity.csv` (the equity at each bar close) and `signals.csv`** (each bar's signal, its change, the net exposure and the order sent): `--export` records the signals as `--plot` does, after the plot is built, so `Result.json` does not grow. **`Run.json` records the code and the environment** — `Revision` (the commit and whether tracked files differ from it) and `Packages` (Python, torch, numpy, polars, pandas) — so a run names what reproduces it.
- **Commission is cTrader's, per side, in cents — measured 2026-09-28.** The Open API's `USD_PER_MILLION_USD` and `USD_PER_LOT` are priced through the base asset (`volume × rate × base→account`), which equals the documented USD route (`base→USD × USD→account`) up to triangulation: on run 5 (EURUSD D1, EUR) `truncate` per side reproduced cTrader's backtester's commission on **510 of 510 trades**, the USD route with any rounding on 87-343. **The engine rounds like the live broker instead — decided 2026-09-29:** every fill's fee rounded half up to the cent, a partial close taking the half-up share of its lot's fee and the lot keeping the exact rest (Live 2: 0.45 → 0.23 then 0.22; a 20 000 position opened in three fills paid 1.81), which moved the goldens' commission a few cents a hundred trades from the backtester's (run 1: −19.48 → −29.80 against cTrader). `PreciseTradingCommissionRate` is ×10^8 **except for `PERCENTAGE_OF_VALUE`, ×10^5** — US500's 1000 is 0.01 %, and the Universe had stored it a thousand times too small until that day. **A minimum commission applies per side, in its own asset** (`Contract.MinCommission`, `MinCommissionAsset` — the quote when its type is `QUOTE_CURRENCY`): a one-contract round trip on US 500, GERMANY 40 and AUSTRALIA 200 cost 7.04 EUR on the EUR demo, 2 × 4 USD; the engine converts it through the quote or base conversion when the asset is one of them, otherwise through its own pair read with the tape (`DatasetAPI.Conversions[2]`).
- **A close takes the position's oldest fills first — 2026-09-29.** cTrader books every closing deal against the lots that opened the position in time order: one trade per closing deal, its entry price the volume-weighted price of the lots it consumed and its entry time the first of them, while the position's own entry price stays the average of every fill (break-even after a scale-out goes to that average). `BacktestingAPI` keeps the lots beside each position (`_lots_`, `_consume_`), each with its own opening commission and spread, so a trade takes exactly the costs of the lots it closed; a position's total P&L is what it was, the split between its trades is cTrader's (run 4's position 64: 7 000 at 0.76003, then 6 000 at 0.757805). **The average entry is exact** — rounding it to five digits after an increase put 50 USD on one live netted deal. Live 1 on the netted demo account reproduced 15 of 15 closing deals to the cent from the broker's fills under both rules, Live 2 on the hedged one 12 of 12. **The live server rounds each deal's commission half up** (0.225 → 0.23) where cTrader's backtester truncates; the engine follows the broker.
- **The minimum commission is charged although cTrader's backtester omits it — decided 2026-09-29.** The live server charges US500's 4 USD a side (7.04 EUR a contract round trip); the backtester charged 0.01 % with no floor (0.72 EUR). Spotware's own answers say backtesting takes a commission per million only; nothing documents a minimum there. The engine models the broker, not the backtester's omission, and the golden records the difference.
- **A stop fires at the first tick at or beyond its level, at the level the engine rounds to the point grid — cTrader's rule, measured.** Firing only strictly beyond it moved every golden away from cTrader (run 3's equal closes 947 → 835), and keeping an opening stop unrounded did too (846 → 813). What remains is 2-7 % of closes a tick or a trailing step apart: every one of cTrader's 3 070 exit fills equals the tape at its millisecond, the stop distances agree to the tenth of a pip cTrader prints, and the level it must have held lies in a band of a few millionths no rounding rule produces — bounded, not fixable from the exports (`RESIDUALS.md`, finding 5).
- **Risk is measured in the account currency — 2026-09-28.** Every sizing function takes the rate it needs: risk divides by `stop × pip × quote-to-account rate`, a notional by the base-to-account rate (`calculate_conversion_rate` refuses a missing rate, `calculate_notional_volume`); strategies read both from the decision bar's close tick (`BidQuoteConversion`, `BidBaseConversion`), which live bars carry too. On 28 pairs × 8 account currencies the risk at a 50-pip stop is 0.968-0.994 %, never above 1 — the shortfall is the volume step. Until then risk was `1 % / price`: 0.0067 % on USDJPY for a EUR account. **The volume floor clamps up:** a raw volume under `VolumeMin` trades the minimum, so a small account can risk more than configured (a 10 000 JPY account, ~60 EUR, risks 5-9 %). DDPG's exposure feature is normalised by the same sizer (`_reference_volume_`).
- **An intrabar event hands the portfolio exactly the ticks it saw — 2026-09-28.** Before a position changes inside a bar — a stop fill, or an open, close, reduce or increase sent at a tick — the engine applies the tape segment since its last cut (`_cut_`, `_segment_`: the segment's open, both sides' extremes and the event tick), and at the bar's close the remainder; a target that changes nothing cuts nothing, since the pieces' union is the whole bar. `PortfolioAPI.update_data` skips a bar whose close it has already seen and a tick older than it; ticks never advance that mark, or a segment cut at the same tick is skipped (found and fixed the same day). Each extreme's P&L uses its own tick's rate. Every trade's excursions equal the tick truth on all five runs and on a live-contract twin; before, run 3 had 483 of 1 024. **A segment of a long bar scans its ticks:** two shortcuts keep that cheap and exact — with no position open only the first and last tick matter, and when the bar's own extreme ticks all lie inside the segment they are its extremes.
- **The position open at the stop is settled — 2026-09-28.** Marked at the window's final tick, charged its closing commission and every roll up to `--stop` (`_settle_`, `PortfolioAPI.settle`), as cTrader closes it. `SpreadPnL` is the spread paid at entry, `(bid − ask) × volume × quote rate`, pro-rated on closes and **part of gross — never add it to net**; it sits between gross and commission in every structure, page and export, and `Spreads Profit/Loss` in `net.csv`.

- **Learning verbosity:** never run H1/large-bar Learning at `Info`/`Debug` — per-bar log flood costs ~0.6s/bar (a 9h hang for one episode). Use `Warning`; spawn workers too.
- **Logging:** silence via sink levels (`log.console.set_level(...)`), never stdlib `logging.disable()` — the fast path bypasses stdlib. `VerboseLevel` is ordered by **verbosity**, so `Debug` is the largest value and a sink accepts `record <= sink` — the inverse of stdlib.
- **Logger identity comes from the calling frame.** A logger built in `Script/Setup/Market.py` renders `Market - Setup` (the `Library` and `Script` roots are skipped); the same call moved into the shared `Script/Task.py` renders `Task - Script`. Never construct `LoggingAPI()` inside a helper on behalf of a caller — pass the logger in.
- **Console encoding:** `·`/`→` crash cp1252 stdout — use `conda run --no-capture-output` and/or `PYTHONIOENCODING=utf-8`, plus `sys.stdout.reconfigure(encoding="utf-8")` in standalone scripts.
- **`QueryAPI` placeholders:** raw SQL cannot use `::type` casts — `::name::` is the interpolation token. Use `CAST(x AS text)` / `to_char(...)`.
- **A table rebuild is not reversible by hand.** `migrate` renames to a temp, recreates, copies, drops — and a rename **carries inbound foreign keys onto the temp**, so without `realign` the drop either fails or silently strips integrity. A `GENERATED ALWAYS` identity rejects a plain insert, aborting the copy *after* the rename and leaving data in `<Table>_<hex>` — recoverable only if the temp survives. Never let a rebuild drop the temp on an unverified row count. **A copied identity must restart after the copied rows:** until 2026-09-28 the Postgres carry left the new sequence at 1, so the first insert after a rebuild collided with an existing UID — the `Universe.Contract` rebuild that day stopped the Universe service on `Contract_UID_key1` until the sequence was set by hand. The carry now restarts every identity at its maximum plus one (Postgres `setval` in the same `DO` block, Oracle `START WITH LIMIT VALUE`; SQL Server's `IDENTITY_INSERT` advances it itself).
- **Two pytest sessions must never share the `Tests` database.** The root `db` fixture drops and recreates the `Universe`, `Market` and `Portfolio` schemas at session start, so a focused run started while the full suite runs wipes the tables under it (2026-09-27: both runs failed, neither for a real reason). Wait for one to finish.
- **Connection count is a correctness budget, not a tuning knob.** Postgres here is `max_connections` 400. Anything holding connections needs a hard ceiling and a return path — verify with a soak (`pg_stat_activity` must plateau), never by watching a page feel faster. A thread-local cache is not a pool: one grew to 409 clients and was reverted.
- **BLAS in standalone scripts:** calling `np.corrcoef`/LAPACK without importing `Library` first can abort the process (exit 127) — set `KMP_DUPLICATE_LIB_OK=TRUE` or import `Library`.
- **A process pool's initializer arguments travel through the spawn pipe.** On Windows the parent writes each child's bootstrap data and then its process object — initializer arguments included — into a pipe, and the child reads the second only after importing the parent's main module; arguments larger than the pipe buffer (measured: 3 KB start in parallel, 70 KB serialize) therefore make every spawn wait for the previous child's whole import — with `Library`, 2.4 s a worker, sixteen workers spread over 36 s and the late ones idle half the sweep. Hand anything large to workers through `ParcelAPI` (`Library/Utility/Memory.py`): shared memory, the pipe carrying only its name. The 100 KB warmup history did exactly this until it was parcelled: all sixteen workers now start within 0.4 s, and eleven years of D1 went 86.1 → 76.9 s.
- **ProcessPool cleanup:** kill worker **children before parents**; orphaned `spawn_main` workers hold ~2 GB each at 0% CPU forever.
- **`psutil` cmdline filters** match your own `python -c "...script.py..."` probe — exclude `os.getpid()`.
- **This repo lives under OneDrive** — `shutil.rmtree(..., ignore_errors=True)` fails silently on sync-locked paths; pass an `onerror` handler and verify with `path.exists()`.
- **Never conclude "no callers" from a truncated search.** A `grep | head` that fills with unrelated matches reads as a clean result and is not one.
- **A private method name is a contract across the class tree.** Twice on 2026-09-28 a new `_name_` on `BacktestingAPI` collided with one on a subclass or parent: the Phase 4 shared-tape `_publish_()` shadowed `SystemAPI._publish_(name, data)`, so every exporting Optimization crashed at delivery, and a new `_release_()` (close the database) was overridden by `OptimizationAPI._release_()` (tear down the pool), so every disconnect rebuilt the worker pool — 26 → 31 s on a 2023 sweep with nothing failing. `Tests/System/test_Backtesting.py` now fails when Optimization or Learning redefines an engine or system private method outside the intended overrides; grep the whole `Library/System` tree before naming one.

## CODING PHILOSOPHY
1. **Precision & Accuracy:** correct, working code over speed.
2. **Simplicity:** do not over-engineer. As simple, concise, readable and performant as possible.
3. **Measure, Don't Guess:** profile before optimizing (`cProfile` by cumulative + tottime, targeted micro-benchmarks). Validate hypotheses with data.
4. **No Environment Configuration:** no `QUANT_*` (or other) environment variables — behavior comes from constructor arguments and CLI flags only.
5. **Generic, never special-cased.** Do not branch on the current context (`if strategy == Download`); keep parallel components symmetric. A special case that solves today's problem is a rule the next component has to know about.
6. **The online backtest is the hot path** — a real strategy, the full engine. Optimize against that, not against a synthetic loop; construction machinery is usually the real target.
7. **Readability beats deduplication.** Explicit methods that repeat a few lines — one per named event, like `StrategyAPI`'s position and order update handlers — read better than a closure factory that generates them. Promote shared logic only when it names a real concept, never just to shorten a file. The same holds for dispatch: `SystemAPI._process_updates_` keeps **one `case` per `UpdateID`** rather than grouped patterns over a class table.
8. **Never run a destructive operation against real data while validating.** Create throwaway rows, on a fresh page with no leftover selection, verify the exact target, then clean up and confirm by query that only your rows changed. A live-DB Scheduler UI validation once deleted a real task because an earlier step had left it selected and multi-select made Delete act on it; its run history was unrecoverable.

## CODING STYLE & ORGANIZATION
1. **Language:** **English (US)** spelling (`Optimization`, `behavior`). Exception: identifiers mirroring an external API verbatim (cTrader's `Cancelled`).
2. **General:** No docstrings or comments. Tidy files (no trailing spaces), **one blank line before a `class` definition**, one blank line after `class` and between methods, and **no trailing newline at EOF**. (Exceptions by explicit request: paper-mapping docstrings in `Library/Model/Method/DDPG|SAC|TD3`, `Library/Model/Core/Noise`, `Library/Strategy/Model` and `Library/Strategy/Hybrid/DDPG.py` — kept for the thesis, including the reward-clipping comment in `Strategy/Model/Reward.py`; API-surface docstrings in `Library/Bloomberg`, `Library/Database`, `Library/Logging`. Do not strip these.) **In the docstring-keeping modules only public API methods get one** — private `_methods_` never do; one documented private among undocumented peers reads as noise.
3. **Naming:** `CamelCase` public members; `_naming_` private; `UPPER_SNAKE` public constants; `_UPPER_` private class constants — **where a class attribute is justified at all (rule 18).** Lowercase `__post_init__` arguments. Paired verbs are `start`/`stop` (never begin/end or open/close — `LogAPI.start`/`stop`, `CycleAPI.start`); the domain noun is `security`, never `symbol`/`instrument`; private data access is `_fetch_` (read) and `_execute_` (write); every API class carries the `API` suffix.
4. **Typing:** simpler types first in a union — `str | MyClass`, never `MyClass | str`. `Self` from `typing_extensions` for instance returns (3.10 compatibility). `from __future__ import annotations` only when forward references require it — a self-reference, a later class, a `TYPE_CHECKING`-only name, a name the module never imports at all, or a class attribute shadowing a type (`Logging/File.py` has a `Path` property, so `Path | str` inside that class body needs the future import). Prefer built-in types over `typing` classes (`type[X]`, never `Type[X]`).
5. **Imports:** sorted ladder-style block; one blank line between external and project (`Library.*`) imports; explicit imports for internal modules. A call or an import is either **entirely on one line or exactly one name per line** — never fill-style wrapping. Package `__init__.py` re-exports run least to most important (flagship API last) — and anything imported there must also appear in `__all__`. Always import `np`/`pd`/`pl` from `Library.Database.Dataframe`, never directly, so the shared display configuration applies — the only exceptions are `Dataframe.py` and its import closure (`Database.Dataclass`, `Utility.Typing`).
6. **Callbacks:** never reference a component by raw string — pass the `ComponentID`, qualified by the declaring class when the reference crosses a class body (`State(SchedulerBaseAPI.TARGET_STORE_ID, ...)`). Declare each shared identifier **once**, on the lowest common base, and let subclasses bind it in `ids()`. Resolution is by name, so a string works — it just hides typos until runtime.
7. **Density:** dense method bodies without internal blank lines (except complex `__init__`); standard spacing in signatures and assignments.
8. **Architecture:** order methods by category (Connection → Disconnection → Business) then by complexity (simplest first); private before public; fields, properties and methods run least to most important. `@staticmethod` for stateless logic, `InitVar` for temporary inputs. **Generic** helpers live in `Library/Utility` — promote repeated logic there instead of duplicating it — and Utility stays generic: no framework vocabulary (run folders, strategy syntax, market horizons, retention policy beyond a default). The market-data download start is `HORIZON` in `Script/Data/Horizon.py` (2014-01-01). Domain constants and helpers belong on the class that owns the concept (`SystemAPI.OUTPUT`, `SyntaxAPI`, `RangeAPI`). **A base class stays generic too:** `AgentAPI` and `NetworkAPI` assume no algorithm and no layer shapes; shared algorithm machinery goes on an intermediate type (`OffPolicyAgentAPI`).
9. **No path arithmetic.** Never `Path(__file__).parent...` — use `Library/Utility/Path.py` (`traceback_root()` for the repo root, `inspect_module(__file__)` for a module's own folder). The single exception is the `sys.path` bootstrap in a standalone entry point, which by definition runs before `Library` is importable.
10. **Dataframes:** capitalize framework-level columns (`Date`, `Security`). Prefer Polars (`pl`); Pandas (`pd`) for compatibility.
11. **Dataclass class constants carry no annotation.** `_DEPTH_ = 3` is a class attribute; `_DEPTH_: int = 3` is a fourth constructor field. Verify with `fields(Cls)`.
12. **`Structure` merges the parent with `**super().Structure` as the last entry** — one idiom, parent columns after the child's, so the physical order is the declaration order. The exception is a child that redeclares parent columns (`TradeAPI` over `PositionAPI`): there the explicit merge loop keeps the child's declaration and lets the parent only fill the gaps, so it is load-bearing, not drift — replacing it reorders or retypes columns and `migrate` would rebuild the table.
13. **Shared status sets live on the datapoint** (`RunAPI.Busy` · `Live` · `Active` · `Open`), never as private tuples on the consumers that read them.
14. **Explicit over loops for small fixed sets.** One line per named attribute, not a tuple-loop — a reader should see the names, and a typo should be a failure at the line that owns it.
15. **Boolean CLI flags are `store_true`** (present = True, absent = False), never `BooleanOptionalAction`.
16. **Prefer `MISSING` to `None` for "not supplied"** (`from Library.Utility.Typing import MISSING, Missing`; `Missing.__bool__` is False). An optional parameter whose default means "the caller gave nothing" defaults to `MISSING` — `DatabaseAPI` routing params (`database`/`schema`/`table`/`legacy`), `InitVar` resolution inputs, `modal_callbacks(opener, closer)`, `NetworkAPI._uniform_(bound)`, `DatabaseAPI.update(parameters)`. Keep `None` only where it is a real value: **persisted datapoint fields** (`= None`, NULL in the table), a value forwarded to an API that gives `None` a meaning (`seed` to numpy/torch, `timeout` to `Event.wait`), or a default handed back to the caller (`Parameter.first(default=None)`).
17. **No module-level functions or variables unless strictly necessary.** A helper that belongs to a class is a static or class method on it (`DatabaseAPI.primary`, `EnumerationAPI.names()`, `ComponentAPI.tip`, `CatalogAPI.resolve`); a callback factory lives in `App/V2/Core/Callback.py` (`modal_callbacks`) or on its page class (`LaunchAPI.launch_callbacks`, `SchedulerEntityAPI.entity_callbacks`). The standing exceptions are pure function modules (the `Utility` helpers, `Statistic/Metric`, `Portfolio/Sizing`, `System/Selection`), constant modules (`Statistic/Label`), decorators applied inside class bodies (`App/V2/Core/Callback.py`'s callback decorators, `Database/Dataclass.overridefield`), `Dataclass.coerce` — called eleven times per `TickAPI`, where a class lookup measured +125 ns — and `Setup`/`Script` entry points. A module's `if __name__ == "__main__"` calls a class method (`CalendarAPI.main()`, `TrayAPI.serve()`). Shared declaration sets get their own class rather than leaking into a page's MRO (`LaunchFieldsAPI`).
18. **Avoid class attributes** — the class-level twin of rule 17. A fixed set of named values is an enum (`AccessLevel`, `Validity`, `CredentialType`); a value that shapes behavior is a constructor argument (`VaultAPI(margin=..., refreshers=...)`, `CommandAPI(refusals=...)`); a value used once is an inline literal; a value used in several places of one class is one small method (`AppAPI._overlay_`). **A class attribute is justified only where a framework contract needs one:** a datapoint's `Schema`/`Table`/`Enums`/`Defaults`/`Nullable`, the `ComponentID` declarations the callback decorators read at class-body time, a page's `_FIELDS_`/`_COLUMNS_` and the `TableAPI` seams (`_ROW_KEY_`, `_SHEET_`, `_NAVIGABLE_`, `_POLL_`, `_FILL_`), and a documented subclass seam (`AppAPI.Launchpad`, `WebAppAPI.Database`). A mutable class-level registry is global state — never write one.

## LOGGING CONVENTIONS
Logs must be short, objective, informative, visually distinctive.
1. **Message Format:** `<Category> Operation: <Outcome> (<primary detail>)`; join extra fields with ` · ` (`Phase Warmup: Completed · 1.20s · 205 Ticks · 41 Bars`).
2. **State Transitions:** `[StateA] → (Reason) → [StateB]`; `→` is reserved for transitions. True changes at `Info`, self-loops at `Debug`, hot-path self-loops silent (`reason=None`).
3. **No Commas or Periods:** ` · ` in place of `,`; one sentence per message; no end-of-sentence periods.
4. **Debug vs Info:** `Info` is strictly trading/execution and periodic trader-useful information; `Debug` is everything else.
5. **Errors:** `<Category> Operation: Failed · <Reason>`, reason capitalized.
6. **Tags:** positional only — no `Class`/`Subclass` arguments. The owning object resolves from the calling frame and always leads (`type(self).__name__`, falling back to the module). With no tags the subsystem is appended (`Library/System/Realtime.py` → `System`); with tags they replace that default and render in order. `LoggingAPI()` in `BufferAPI` gives `BufferAPI - Database`; `LoggingAPI("Buffer Management")` gives `BufferAPI - Buffer Management`. `identify=False` drops identity entirely. Process-wide run identity (provider · ticker · timeframe) belongs in `LoggingAPI.set_shared_tags(...)`, rendered *before* the level.
7. **Capitalization:** Title Case for fixed labels and nouns; capitalize the leading word of free-text reasons.
8. **Verbose Levels:** entry points set both primary sinks explicitly through a logger instance — `log.console.set_level(...)` / `log.file.set_level(...)` — never through the class. Sinks are process-wide, so the outermost `with log:` locks them. Use `with log.console.temporary(...)` for a scoped change.
9. **Lazy Messages:** pass a `lambda`, never a built string — `log.debug(lambda: f"...")`. A rejected record costs ~128 ns instead of rendering a thrown-away f-string or dataframe. Capture loop/`except` variables with default arguments (`lambda error=error: ...`). Bare constants are fine.

### Python (`Library/`)
- **A select's empty option names its placeholder — 2026-09-27.** `dbc.Select` always renders a hidden `<option value="">` first, so an option whose value is `""` ("(none)", "Owner", "(server zone)") was shadowed by it and the field showed blank whenever its value was empty. `SelectAPI` takes that option's label as its placeholder, so the hidden option shows the same text; a select whose options arrive by callback declares its empty option in the field itself so the label exists at build. Automation that selects by label must pick the visible option — the hidden one now shares its label and is disabled. **A tooltip never takes a click:** `.tooltip { pointer-events: none; }` — after a refused save the focused Apply button's tooltip sat on top of Cancel and swallowed it.
- **`Library/App`**: Versioned Dash framework — `V1/` frozen legacy (critical bugfixes only), `V2/` active; consumers pin a version (`from Library.App.V2 import AppAPI`) and the versions share zero code. `AppAPI(ShellAPI, RouterAPI)` — Shell owns layout + navigation tree, Router owns path resolution and the single-paint route callback. **`V2/` is split into subpackages** — `Core/` (Callback · Injection · Identity · Layout · Router · Shell) · `Component/` · `Page/` · `Lightweight/` · `Session/`, with `App.py` at the root; the parent `__init__` imports **through** those packages, never past them into leaves. `AppAPI.Launchpad` names the root page class and `LaunchpadAPI._MATRIX_` pins its grid as `(columns, rows)` — empty keeps the CSS auto-fit. **An application may overlay the framework assets:** Dash keeps serving `App/V2/Assets`, while a folder named `Assets` beside the `AppAPI` subclass is consulted first by `asset()` and served at `/_application`. Repointing Dash's own `assets_folder` instead silently drops the auto-injected `Scripts/*.js` and the favicon. `Lightweight/` is the **only** charting/tabling system (Dash `DataTable` retired 2026-08-03). **The spec layer is `Library/Statistic/Workspace.py` and imports no Dash.** `Workspace.backtest(...)` is the single composition of a result view, rendered by both `--plot` and the web pages. **Artifacts are immutable** — a run's page renders the HTML written when it ran, so new panes do not appear on old runs.
- **`Library/Auth`**: Server-side authentication + RBAC on the Postgres `Auth` schema. `RoleAPI` (`Public` < `Viewer` < `Editor` < `Moderator` < `Administrator`), Argon2id `PasswordAPI`, `UserAPI`/`TeamAPI`/`OfficeAPI`, provider seam (Local · Cloudflare · OIDC), `AuthAPI`, and `Access.py` — `AccessLevel` (`Denied` · `View` · `Run` · `Edit`) and `AccessAPI`, **the one implementation of the owner-and-thresholds rules** that the credential and scheduler managers both call (`validate` · `allows` · `claim` · `label` · `roles`). Zero environment coupling: constructor params only; the web app passes the stored `SessionAPI.secret`, so a server restart keeps everyone signed in. Seeded by `Script/Setup/Auth.py`.

- **`Library/Protocol`**: Wire protocol shared with the C# Connector — `Action/` and `Update/`, `ActionID`/`UpdateID`.
- **Two thresholds decide who may use and who may change — on a credential, a workflow and a task.** `ViewRole`/`EditRole` on `Credential`, `RunRole`/`EditRole` on `Workflow` and `Task`, each a `RoleAPI` level meaning "this role and above", each validated on save: **`Public` is refused**, **null means owner only** (plus `Administrator`, who reaches everything), **neither may exceed the setter's own role** — a higher threshold would lock the creator out of what they just created — and **`EditRole` is at least `ViewRole`**, since the edit form reveals the value. The owner always keeps access, and a user who owns rows cannot be deleted. **Enforced in both managers through `AccessAPI`, 2026-09-23:** every mutating call takes `by` — a user UID is checked, `MISSING`/`None` is a trusted framework caller (the installer, the daemon, a script), and an unknown UID is refused. Only a signed-in user may create; a non-`Administrator` may only own what they create; only the owner or an `Administrator` transfers; an unchanged threshold above the editor's role survives an edit (only a *changed* value is capped); a create over an existing UID needs `Edit` on it; joining or leaving a workflow needs `Edit` on the workflow; skip, cancel, approve, reject and retain need `Run` on the run's task, delete needs `Edit`. **Both thresholds default to null (owner only)** — the one default that never trips the cap. The `Administrator` backfill in `Setup.Scheduler` was **removed**: it rewrote every legitimate null on each Setup run. The installer registers infrastructure at `Administrator`/`Administrator` and the three `Research.*` tasks at `RunRole` `Editor`, the Launch page's own audience. **A run uses its task owner's credentials, not the starter's**, so `RunRole` grants use without sight; `Run.Auditor` records who pressed start (`ManagerAPI` → `ExecutorAPI.spawn(auditor=)` → `Runner --auditor`), and a run with arguments gets `--user <owner>` appended beside `--run`, which `Library/System/Main.py` records as `User` in `Run.json`. - **`Library/Scheduler`**: DB-backed job orchestration on the Postgres `Scheduler` schema, replacing Windows Task Scheduler with one boot daemon. `WorkflowAPI` → `CycleAPI` (one execution of a workflow) → `TaskAPI` → `RunAPI`; `RunStatus` runs in lifecycle order (`Waiting` · `Initializing` · `Running` · `Terminating` · `Approving` · `Reviewing` · `Retrying` · `Success` · `Failure`, 2026-09-29) — rows store the name, so the numbers are free to move; `DependencyAPI` holds DAG edges, evaluated by `CoordinatorAPI`. One shared `Kind` ∈ {`Manual`, `Scheduled`, `Service`} spans the module. **Every run goes `Initializing` → `Running` → `Terminating` — 2026-09-27**, scheduled tasks and services alike: a run reports its phase with one sentinel line the executor parses like progress (`ProgressAPI.phase`), which the shared plumbing emits at its own boundaries — `CommandAPI` around `run`, `Script/Task.py`'s `attempt` around the work, `DataServiceAPI` when a service is ready and when it stops — and a test holds every registered task to one of them. **`Waits` means until the predecessor is useful:** after a service, `Running`; after a scheduled task, its closing status as before. **Only the workflow `Schedule` opens a Cycle**; a member task's `Schedule` is an earliest-start gate *inside* it, never a trigger. `ManagerAPI` is the single mutation authority behind console, CLI and web. **A suspension is not a failure** — `_service_` closes the run `Success` stamped `Suspend` when the daemon itself terminates a service for maintenance; leaving it to the reaper recorded 29 healthy tunnel runs as crashes. Stopping the daemon — the tray's Quit, Shutdown or Restart — closes the services it terminates the same way; until 2026-09-26 the reaper recorded them as `Failure` a lease later. The tray's Restart goes through the logon launcher, so a validated environment is applied on a restart as on a logon. **Boot launch continues an open cycle** instead of opening a second one after it. **A run the daemon cannot classify keeps its cycle open — 2026-09-28:** the daemon asks whether a run has ended (`RunAPI.Ended`, `Success` or `Failure`), never whether it is active, because the runners it spawns load the working tree and it does not: on 2026-09-27 a daemon started before `Initializing` existed saw the Environment and Web runners report it, took them for finished and closed both 03:00 cycles as `Failure` 23 s in, before `Cache` and `Retention` could run. **A service waits only for its own scheduled ancestors — 2026-09-27:** while its workflow's latest cycle is open, a service stops (closed `Success` · `Suspend`) and stays down until every scheduled task upstream of it in the DAG has run in that cycle — not merely finished since the daemon started, which let services restart for a moment between two maintenance tasks (a 0 s Server run at 00:12:03 on 2026-09-26) — and an unrelated task of the same workflow no longer stops it. A task awaiting approval or review releases it, as before. **Workflows can depend on workflows — 2026-09-27:** `Workflow.After` names an upstream (a foreign key, `ON DELETE SET NULL`); while the upstream's latest cycle is open, a due cycle of the dependent opens as **`Waiting`** (so its schedule counts as fired), dispatches nothing and is released to `Running` when the upstream closes, whatever its outcome — a manual run waits the same way — and the dependent's services do not start meanwhile (running ones keep running). A disabled upstream holds nothing. Logon launches every service-bearing workflow's upstreams too. `ManagerAPI` refuses an unknown upstream, the workflow itself, a loop, or one the setter cannot see; an empty value clears it; the CLI takes `--after`. `Environment`, `Web` and `Data` are registered independent — nothing in the 04:00 cycle touches `Quant` any more, so nothing needs to wait. **A runner owns its child, however it dies — 2026-09-24.** `ExecutorAPI.run` tethers the child to a Windows job object with kill-on-close (`Runtime.tether`/`release`), so a runner that crashes or is killed from outside takes the service with it, and a `try/finally` stops the child if the monitoring loop raises. A failed heartbeat write is logged (`Run Heartbeat: Missed`) instead of ending the runner. Before this, a 30-second Postgres restart on 2026-09-23 killed both service runners on their heartbeat write, orphaned the web server and the tunnel, and the daemon started second copies beside them — the "restart did not quite work" seen more than once. `ManagerAPI` opens a connection per call deliberately.

Measured 2026-09-25 (first run from the database · again on the dataset in memory): H1 2023 `Auto` 2.83 · 1.28 s, `T1` 2.99 · 1.33, M1 3.45 · 1.34, bar level 2.95 · 1.34; D1 2015-2026 `Auto` 6.06 · 0.78, `T1` 6.44 · 0.88, M1 9.65 · 0.78, bar level 6.04 · 0.75; H1 2015-2026 `Auto` 23.35 · 13.01, `T1` 25.11 · 14.08 — `Auto` costs what the bar-level walk costs. The walk is a small share of a run (0.19 of 10.7 s on golden 5); the rest is the read, the bars and the strategy. The deleted ladder (H1 and M1 bars built for the whole window, 4.4 s of preload on eleven years, to save a walk worth 0.2 s) made the old `Auto` slower than `T1`. The M1 walk used to send every point through Python (20.4 M on golden 5, 82 s profiled) and now takes 10.5 s, its exports identical. **Every resolution is the tick walk over a smaller set of real ticks — 2026-09-25.** A coarser resolution walks, per bar of that resolution, its distinct ticks in time order: the open, the tick where the ask was highest, where the bid was highest, where the ask was lowest, where the bid was lowest, and the close — never a bid extreme standing in for an ask one, never one tick twice (the tick walk never re-checks a tick either). Tick bars (`T10`) are continuous n-tick bars built the same way; until today they took their extremes from the bid alone, which cost 127 of 1 024 trades on golden 1 against the tick walk. **One fill rule everywhere:** an event fires at the first walked tick beyond its level, at that tick's own timestamp, and fills as that order type fills at tick resolution — a stop loss at the tick's market price, a take profit at its level (a limit never fills worse than its price), a target hands the tick to the strategy, whose orders fill at its market price. Measured 2026-09-25 against the tick walk on goldens 1 and 5 at M1, T10, H1 and D1: this rule came out below the tick result in all six cases (−10 to −2 309); pricing a crossing behind hidden ticks at its level instead came out above it in four of six (up to +774) and worse at T10, so it was not taken. Skipping points that cannot fill changes which points draw a `Random` spread, so a `Random` run differs from one that walked every point; every deterministic spread is identical. Tick stamps stay milliseconds, as views of the tape. **Conversions are looked up per event** from the pair's own tape (`DatasetAPI.Conversions`, `TapeAPI.rates`), never stored per tick, and a pair whose tape starts after the run's is refused. **Ticks are released when a run cannot walk them — 2026-09-25.** A bar-level or finer resolution keeps only the bar rows, the finer bars' points and the conversion rates at the timestamps it can visit (`_reduce_`, every lookup identical); the warmup history keeps its materialised rows, never its tape. Eleven years of EURUSD H1 after load: 7.54 GB at `Auto` (which walks the ticks), 1.74 GB at M1, 0.94 GB at bar level, exports identical. The tape still exists while the bars are built. **Optimization and Learning workers share one copy of every tape — 2026-09-25.** Before its first pool the parent reads the traded tape over the whole run range, and each conversion pair a week wider, straight into named shared memory (`TapeAPI.read(shared=True)`, owned by a `ShareAPI`); workers receive handles, map the blocks read-only (`ShareAPI.attach`) and cut every window from them (`TapeAPI.cut`, the same ticks and volumes a read returns); anything outside the shared range still reads from the database. The parent frees the blocks in `finally`, and Windows frees a block when its last handle closes, so a crash leaks nothing. **Views are built with `np.frombuffer`, never `np.ndarray(buffer=...)`:** the latter drops its buffer export at once, so closing a block under a live view unmapped it and the next read was an access violation, not an exception; `frombuffer` holds the export, so a close under a live view is refused and the pages go with the last view. Bar starts are found in 4 M-tick chunks, so a worker never allocates a key per tick. Measured on eleven years of EURUSD D1 at `Auto`, 652 candidates: 4 workers 325.5 s and 28.7 GB of system memory before, 128.0 s and 17.3 GB shared; 16 workers 81.9 s and 20.9 GB (6.6 GB shared plus about 0.9 GB a worker, mostly imports); 654 of 654 scores identical on a 2023 sweep, and a two-seed Learning run identical seed for seed. **The warmup history is shared the same way:** before each pool the parent takes the widest window its candidates need (`SystemAPI._widest_`, the same indicator windows the engine warms to — Learning has one parameter set, so one window), reads that much history once per scope start (`BacktestingAPI._histories_`) and hands it to the workers; every candidate still takes exactly its own window from its tail, because warming a candidate to a wider window than its own moves its score ("Do not warm every candidate"). No worker reads the database for its warmup any more: eleven years of D1 at 16 workers, worker warmup 61.2 → 0.07 s and worker time 806 → 587 s; the 2023 sweep's 654 scores and the Learning seeds identical, walk-forward folds included. **One pool per fold:** the pool outlives a round — every round and stage of a fold reuses its warm workers, scope and history already loaded, and it is rebuilt only when the fold changes or a round needs a wider history (`OptimizationAPI._acquire_`/`_release_`). A grid is cut into chunks of at most eight candidates and never fewer tasks than workers, so a 7-candidate round runs on seven workers instead of one (7.4 → 0.6 s a round). **The parent reads the tape once:** a run that fans out (`_spawns_`) publishes the shared tapes on its first connect and preloads from them (`_publish_`), so the traded tape is read once instead of twice and the parent holds no private 7 GB copy; and each pool receives its fold's bar index with the parcel (`_shared_bars_`, `TapeAPI.span(bars=)`), so no worker rebuilds the bars (102 → 6 s of worker time). Eleven years of D1 at 16 workers, 85.2 s this morning → 51.0 s; the 2023 sweep at 4 workers 35.0 → 22.8 s; every score and Learning seed identical. **`readers` (32) bounds the tape's connections and threads**, divided by `--workers` in every Optimization and Learning worker payload, so a process pool never exceeds the connection budget. **A cBot run stores no market data** — the market buffer and the `--market-*` flags went with Phase 3. **A replay keeps its database connection (2026-09-28):** `_replay_` resets the system and reuses the connection, `_hangup_` closes it only at disconnect — an Optimization candidate reconnected on every replay, 34 ms each.
- **`--continuous` interacts with election and must be reported as such.** Continuity makes folds path-dependent — every fold starts near the previous winner — so `Frequency` election becomes near-tautological because the folds agree by construction. at midnight re-fetch the finished day and compress every chunk that ended before it; a failed day is retried hourly; a day is replaced in one transaction, so a reader never sees it half written; **a day written after its successor rewrites that successor** (`DownloadAPI.successor`, skipping empty days), because a day's first ticks carry the side the server did not send from the last stored tick before midnight — 59 days written out of order by retries and restarts had carried a side from an older day, up to 126 pips away) · `PortfolioWorkerAPI`/`PortfolioServiceAPI` (mirror orders, deals as trades, open positions and cash flows every 5 s, resuming after a restart from `Account.Timestamp`, stamped only when a sync completes; **read-only by construction** — no execution API — and **demo accounts only**; derived fields computed through `ReplayAPI` for the pending positions alone once `Market.Download` covers their holding window, and a trade no tick saw open takes its exit as both excursions) · `CalendarServiceAPI` (missing and incomplete weeks first, then the current week every 5 minutes and while a release is due, the next week every 6 hours; a page without calendar data is a named failure; **a week runs Monday to Sunday, everywhere** — `week_start` in `Utility/Datetime`, on `Weekday.Monday`, is the one definition, and Postgres's `DATE_TRUNC('week')` agrees — while a Forex Factory page runs Sunday to Saturday (verified 2026-09-28), so `CalendarAPI.week` reads the two pages a week spans and keeps its seven days. Until then it read one page, the one holding the Monday, so a week's Sunday — the Sunday-evening Asia-Pacific releases — was never read with it: a JPY release at Sunday 23:50 UTC stored its actual 14.5 minutes late, after the next week's page was read at midnight).
- **Every stored task path points into `Script/`,** so moving `Library` code never breaks a Scheduler row. A script that only wraps a library class stays three lines (`Web/Server.py` builds `WebAppAPI.build()` into the web tray; `Data/Calendar.py` calls `CalendarAPI.download`). Moving a script means updating `Scheduler.Task.Path` — `python -m Script.Install --register` re-registers without provisioning, but it rewrites every field of every task (including `Enabled`), so for a pure move update `Path` alone through `ManagerAPI.update_task` and confirm every stored path exists.
- **One boot entry.** Windows Task Scheduler runs only the launcher (`Quant Scheduler` logon task → **base** `pythonw Script/Scheduler.py`), which applies a validated `Quant.next`, starts `envs\Quant\pythonw Script/Scheduler.py --daemon` — the silent tray daemon — and exits, so the task's own run limit (Windows' default three days, the task sets none) never reaches the daemon; the daemon is started breakaway from the task's job where Windows allows it. Run under any other interpreter, the launcher hands over to base first. The daemon boot-launches service-bearing workflows and their upstreams, supervises services, cron-launches scheduled workflows and advances manual ones. `Scheduler.py` imports nothing from `Library` outside `--daemon`, so it runs whatever state `Quant` is in.
- **Three standard workflows** (registered by `Script/Install.py`, owned by `Script.Setup.Auth.ADMIN`): **`Setup`** (manual) = the FK-ordered provisioning DAG (`Enums` · `Auth`→`Credential`→`Logging`→`Scheduler` · `Universe`→`Market`/`Portfolio` · `Indicator`, all `Tolerates=false`; `Credential` follows `Auth` because its `Owner` references `Auth.User`, and `Logging` precedes `Scheduler` because `Run.LID` references `Logging.Log`); **`Environment`** (daily `0 4 * * *`) = `Update` → `Cache` → `Retention`; **`Web`** "Web Application" (daily `0 4 * * *`, services always on) = `Version` → `Tunnel` → `Server`; **`Data`** "Data Intelligence" (daily `0 6 * * *`, services always on) = `Credential` → `Universe` → `Market` → `Portfolio`, and `Credential` → `Calendar` on a branch of its own. Split on 2026-09-27 from `Environment` and `Market` by `Script/Setup/Workflows.py`, which moved five tasks with their runs and Market's cycles.
- **Provisioning tasks** (the `Setup` workflow) are idempotent modules with a uniform `main(database="Quant") -> int` — re-run any task or the whole DAG safely; each also runs standalone (`python -m Script.Setup.Auth`). Of the `Environment` tasks, `Update` and `Cache` take no `database` argument; `Retention` takes one because it also prunes `Logging.Log`.
- **Shared plumbing is `Script/Task.py`** — `migrate(db, *datapoints)`, `attempt(log, name, work, *, detail)` (runs a callable, logs Completed/Failed, returns the exit code) and `provision(log, name, work, *, database, detail)` (`attempt` inside a Postgres connection). **Both take the logger and never build one** (see the logger-identity trap). `Logging`, `Universe`, `Market`, `Portfolio`, `Scheduler` and `Indicator` use `provision`; `Auth`, `Enum` and `Update` use `attempt`.
- **The enum block providers declare, they do not run.** `Action` · `Position` · `Strategy` · `Stream` · `System` · `Update` are five-line modules exporting one `*_block()`, and `Logging` exports `logging_block()` beside its provisioning task; `enum_block(name, enumeration)` takes the enumeration itself. `python -m Script.Setup.Enum` is the single entry point. Guard any generator change with the output hash — the committed `Enum.cs` is `0e4376eb0965433a` (sha256, first 16; since 2026-09-28, when `StrategyType.Test` became 5 — `dce822655ff78ae7` before it, from 2026-09-27, when `StrategyType.Download` and `UpdateID.Batch` went and `Complete` became 82; its header names `Script/Setup/Enum.py` since 2026-09-17).
- **One-off migrations live in `Script/Setup/`** — `Timezone.py` (local → UTC stamp conversion) is dry-run by default, applies once, and records a marker; it is not part of any workflow. `--apply` runs every column in one transaction and writes the marker only after the commit. `Tape.py` and `Reload.py`, which built the UTC tape and a reload of the old one, were deleted with the old tables at the switch; their lessons are in "The tick tape".
- **Entry point:** `python -m Script.Install [--database] [--boot] [--register]` provisions in-process, registers the workflows, with `--boot` creates the Windows logon task, and with `--register` only re-registers.
