# Architecture

Detailed design notes and the rationale behind them. `RULES.md` carries the conventions, the traps
and the index; this file carries the depth. Split out 2026-09-03 because `RULES.md` is loaded into
every session and this material is only needed when working in the area it describes.

Every measured number here was measured. Do not re-litigate a decision without re-measuring it.


### Python (`Library/`)
- **`Library/App`**: Versioned Dash framework — `V1/` frozen legacy (critical bugfixes only), `V2/` active. The package root re-exports nothing: consumers pin a version explicitly (`from Library.App.V2 import AppAPI`); versions share zero code. **`V2/` is split into subpackages** — `Core/` (Callback · Injection · Identity · Layout · Router · Shell) · `Component/` (Component · Chart · Field · Notification · Breadcrumb · Segment) · `Page/` (Page · Launchpad · Login · Settings · Form) · `Lightweight/` (Lightweight · Table) · `Session/`, with `App.py` at the root, and the parent `__init__` imports **through** those packages rather than past them into leaves. `App.py` is the composition root; `Core/Shell.py` (`ShellAPI`) owns the header/menu/body/footer/modal/hidden layout builders and the navigation tree, `Core/Router.py` (`RouterAPI`) owns path resolution (`resolve`/`anchorize`/`endpointize`/`locate`/`redirect`) and the single-paint route callback — `AppAPI(ShellAPI, RouterAPI)` inherits both, so the MRO callback walk still registers everything once. The root page class is `AppAPI.Launchpad` (a subclass seam) and `LaunchpadAPI._MATRIX_` pins that page's tile grid as `(columns, rows)` — empty keeps the CSS `auto-fit`, `(4, 2)` pins both, `(6,)` pins columns only. **An application may overlay the framework assets:** Dash keeps serving `App/V2/Assets`, while a folder named `Assets` beside the `AppAPI` subclass is consulted first by `asset()` and served at `/_application`. Repointing Dash's own `assets_folder` at the application instead — which the first implementation did — silently drops the eight auto-injected `Scripts/*.js` and the favicon, since only stylesheets were re-added. The header **degrades by measured fit, never by a width breakpoint**: `Assets/Scripts/Menu.js` compares brand + nav + account against the header on resize/orientation/route change and applies `app-header-tight` (drop the team line) → `app-header-lean` (drop the brand titles) → `app-header-compact` (nav behind a hamburger), so an 11-inch iPad and a 12.9-inch one collapse at their own points and a page with a longer nav collapses sooner. V2 integrates `Library/Auth` opt-in (`AppAPI(auth=..., access=...)`): the router gate enforces `max(app.access, page.access)` per page, anonymous visitors are redirected to `LoginPageAPI` at `/login`, authenticated-but-underprivileged users get the forbidden layout, and the router mirrors the server session into the client `user` store (name label + per-role icon tint). `Lightweight/` is the **TradingView-backed charting + tabling system** and the only one — the Dash `DataTable` implementation was retired on 2026-08-03, so `TableAPI` in `Lightweight/Table.py` *is* the Lightweight grid page. Layers: typed spec dataclasses (`SeriesAPI`/`PaneAPI`/`MarkerAPI`/`LineAPI`/`SpanAPI`/`DealAPI`/`ColumnAPI`/`SheetAPI`/`WorkspaceAPI`, plus `PointAPI` data helpers — `candles`/`line`/`conform`/`rebase`/`decimate`/`thin`/`cell`) feed `LightweightChartAPI` (multi-pane synced charts: candles/line/area/histogram/bar/baseline, markers, deal map, threshold bands, cross-pane crosshair + range sync) and `LightweightTableAPI` (virtualized grid — only visible rows in the DOM, client-side sort, single/ctrl/shift selection, sheet tabs, row→chart drill-down, double-click row → detail page), composed page-level by `TableAPI` (`_columns_`/`_rows_`/`_fingerprint_`/`_detail_base_`/`_actions_`/`_extras_` plus the write surface — `_EDITABLE_` turns on `_editable_columns_`/`_write_`/`_append_`/`_remove_`, an Insert and a Delete button, and double-click-to-edit on every writable cell; the key column is never writable and polling is suspended while a page is editable so a refresh cannot clobber an open input). `TableAPI.sheet(...)`/`.workspace(...)`/`.table(...)` build a standalone sub-grid for detail pages. Payloads travel in a hidden `<script type="application/json">` carrier (a plain serverside callback on its `children` refreshes it — no clientside bridge needed); selections travel back through a companion store via `set_props` (payload: `selected` uids · `indices` · `rows` — the selected records, so button gating stays clientside — `total`/`shown`/`sheet`/`base`/`key`), and cell edits through a second store as `{uid, column, value, sheet, stamp}`. Selection repaints toggle a class in place rather than rebuilding the row nodes, so a click never detaches the element a double-click or an open editor is anchored to. The vendored library lives at `Assets/lightweight.js` (**v5.2.0, pinned — upgraded from v4.2.3 on 2026-07-31**; v5 replaced `addXSeries` with `addSeries(LightweightCharts.XSeries, …)` and moved markers to the `createSeriesMarkers` primitive, so a bump is a code change, never a drop-in — verify a rendered `--plot` before trusting one), the renderer at `Assets/Scripts/Lightweight.js` (mount/dispose on a `MutationObserver` because the SPA router swaps content and `on_leave` fires too late), the palette at `Assets/Styles/lightweight.css` as `--lw-*` CSS variables for light and dark. The charts view carries a **date-range brush above the panes** — drag the window to pan, its grips to zoom; it follows any chart's `visibleLogicalRange` and drives every chart back, so the visible span is always legible as dates. Every pane has a **collapse chevron** (collapsed panes shrink to their header and the time axis moves to the last expanded pane), and the chart host takes `height="fill"`, which measures the space left to the footer on mount/resize/orientation instead of a fixed `vh` — a fixed value left dead space on tall screens. The **deal map encodes two channels**: segment colour is profit/loss (green/red) and the entry/exit dots are direction (blue Buy · orange Sell), with a per-side toggle each. The segments are 3 px because they otherwise share the candles' exact green and red and read as if drawn behind them — verified they are not: hiding the candles changes visible deal pixels by 6 of 1540, which is anti-aliasing. Deal series declare `autoscaleInfoProvider: () => null`, without which toggling them re-scaled the price axis. **Every pane hides its left price scale and pins the right one to a fixed 84 px** — series on the left axis keep independent autoscaling but draw no axis, and without the pin the right scale sizes to its label text, so plot areas differed by up to 22 px and the shared crosshair stepped sideways between panes. `Assets/Scripts/Archive.js` is the download seam: a dependency-free store-only ZIP writer (CRC32 + local headers + central directory, verified against Python's `zipfile`), plus `csv`/`capture`/`sheetCanvas`/`save`. Download and Export each emit **one** file — browsers block a loop of saves from a single gesture exactly as they block a loop of `window.open` — with a per-pane and per-sheet `⤓` beside the global buttons. **The spec layer lives in `Library/Statistic/Workspace.py` and imports no Dash** — `Lightweight.py` holds only the Dash components on top of it. `backtest()` now defaults to `markers=False, dealmap=True`: the deal map draws a green (profitable) or red (losing) segment with a dot at entry and exit, solid for Buy and dashed for Sell, which reads like cTrader instead of a field of arrows and squares. Because artifacts are immutable this only affects newly written plots. `Workspace.backtest(...)` is the **single composition** of a result view (price · direction · volume · accounts · growth · underwater · rolling panes, spans, deal map, and the `Positions · Trades · Deals · Net · Benchmark · Excursion · Distribution · Monthly` sheets); `--plot` renders it through `WorkspaceAPI.document()` to a self-contained HTML file and the web pages mount the very same workspace, so the view is defined exactly once. The analytics beside it are pure functions over the equity curve — `underwater` · `overwater` · `periodic` · `rolling` · `covariant` · `distribution` — `overwater` is the deliberate mirror of `underwater`: rise above the trough **since the last equity peak**, so both return to zero at every new high. Measuring it from the all-time low instead (as `Portfolio._accumulate_excursion_` does for the `Max/Mean Equity Runup` *metrics*, correctly) makes the per-bar chart trace the equity curve on any uptrend, which is not a runup curve. The metrics were left untouched. Plus `excursion(bars, trades)`, which derives **per-trade MAE/MFE at bar resolution** from data already in the payload (peak/trough between entry and exit) rather than from engine state, so it adds a sheet without touching the goldens. `Workspace.compare(entries)` is the **run-comparison** composition: it lifts each run's rebased growth curve and Net/Benchmark metrics straight out of the stored plot payloads (`trace`/`tabulate`) and returns one growth pane plus a metric-per-row sheet. Two rules there earn their keep — every curve is reduced to **one point per day** (`diurnal`) because Lightweight's time scale is index-based, so an H1 run's 6k points would otherwise swamp two D1 runs and bend the axis out of linearity; and `tabulate` reads the **`Net Total Metrics (Individual)`** column by name, never `row[-1]`, because the last column is *Aggregated* and disagrees with the Trades sheet (golden 18: 37 individual vs 25 aggregated). A comparison is addressed by joining uids with `+` in the existing parametric detail route (`/backtesting/<uidA>+<uidB>`), so it needs no new page, route, or navigation entry, and it mirrors the single-run surface: it opens on **Overview** with the same metric groups rendered one row per run (`_panel_` builds the grid for both), then Charts and Tables. **Artifacts are immutable records**: a run's page renders the HTML written when it ran, so panes added later do not appear on older runs until they are re-plotted. `Page/Page.py` owns `PageAPI` (the `_icon_`/`toolbar`/`register` helpers) and `RefreshAPI` — the **single** fingerprint-gated refresh loop (`_refresh_ids_`/`_fingerprint_`/`_refresh_button_`/`_polling_` plus the `_enter_`/`_refresh_`/`_tick_` callbacks) mixed into both `TableAPI` and any detail page that polls. `Core/Identity.py` holds `GlobalAPI` — the 64 app-global `ComponentID` declarations that `AppAPI` inherits; every page imports it instead of `AppAPI`, so a callback can name a global identifier without a circular import. `Component/Breadcrumb.py` is the reusable trail (`CrumbAPI` label+href, `BreadcrumbAPI` renders links · separators · a non-linked current crumb) — any page declares a lineage and the framework renders it. The shell is responsive: `AppAPI._META_` ships the `width=device-width` viewport (without it iOS lays out at 980px and zooms out) and below 900px the top navigation collapses behind `GLOBAL_NAVIGATION_TOGGLE_ID`, a hamburger left of the account menu, closed again by `Assets/Scripts/Menu.js` on any outside click. `Component/Field.py` is the **declarative form spec**: a `FieldAPI` entry carries its own `ComponentID`, control kind, label, help, DB column, default (value or `page ->` callable), grouping and `decode`/`encode` hooks, so one `_FIELDS_` tuple drives registration, the modal body, the create defaults, the edit round-trip, the save payload, the required-field message **and** the read-only detail view. Callback decorators expand it inline (`*Entity._outputs_(_FIELDS_)` / `*Entity._states_(_FIELDS_)`), so adding a field is one line instead of five aligned edits. `Component/Chart.py` holds the figure components — `PlotlyAPI` and `NetworkAPI` (the reusable **networkx dependency graph**: `render(nodes, edges)` lays out a DAG with `multipartite_layout`, colors each node, reports an empty set or a cycle through `blank(...)`, and ships zoom/pan disabled so a touch drag scrolls the page instead of the plot; `anchor=` wraps it in a `data-open` host and `Assets/Scripts/Dag.js` turns a **double-click on a node** into a jump to that entity's page — the uid rides in `customdata` and the edge trace is `hoverinfo="skip"` so it never wins the hit test).
- **`Library/Auth`**: Server-side authentication + RBAC on the Postgres `Auth` schema. `RoleAPI` (`Public` < `Viewer` < `Editor` < `Moderator` < `Administrator`, `grants()`), `PasswordAPI` (Argon2id hash/verify/rehash), `UserAPI`/`TeamAPI`/`OfficeAPI` datapoints, `IdentityAPI`/`AnonymousAPI` (Flask-Login users), the provider seam (`LocalAuthProviderAPI` · `CloudflareAuthProviderAPI` · `OIDCAuthProviderAPI` — SSO users JIT-provisioned by email as `Viewer`), and `AuthAPI` (installs Flask-Login + `ProxyFix` + hardened cookies; `find`/`locate`/`authenticate`/`login`/`logout`/`provision`/`create`/`touch`/`password`). Zero environment coupling: `AuthAPI(secure=True, secret=None)` constructor params only (no secret ⇒ fresh random per process ⇒ restart forces re-login). Seeding via `Setup/Auth.py`.
- **`Library/Bloomberg`**: Bloomberg API integration (`HistoricalAPI`, `IntradayAPI`, `ReferenceAPI`, `StreamingAPI`, `QueryAPI`).
- **`Library/Database`**: Database abstraction layer (`DatabaseAPI`, `DataclassAPI`, `DatapointAPI`, `QueryAPI`, `EnumerationAPI`, dataframe utilities). Oracle, Postgres, and SQL Server subpackages. **Migration seam — four hooks, driver-specific because no two engines agree here:** `disordered()` compares physical against declared column order and feeds `diff()`, reading the standard `information_schema` in the base (Postgres and SQL Server share it) with Oracle overriding `_ordinals_` for `all_tab_columns`; `_carry_()` returns the **whole** copy statement a rebuild inserts through, because a generated identity is lifted differently everywhere — Postgres takes an inline `OVERRIDING SYSTEM VALUE`, SQL Server needs `SET IDENTITY_INSERT` *around* the insert (session-scoped, so it must ride in the same execution or be stranded), Oracle needs the column flipped to `BY DEFAULT` and back inside a PL/SQL block; `realign()` re-points the inbound foreign keys that a rename dragged onto the temporary copy — leave them and the drop either fails or takes referential integrity with it. A rebuild also **counts rows before dropping** and refuses if they disagree. Only the Postgres path is proven against a live server (the 148 GB `Market.Tick` rebuild); Oracle and SQL Server carry statement-shape tests only. **Connection scope:** `scope()` binds one connection to a unit of work and every `attach()` nested inside reuses it — generic on `DatabaseAPI`, no driver code. The binding lives in a `ContextVar` (concurrent requests never see each other's connection), is **lazy** (a scope that touches nothing costs nothing), and is released at block exit — a connection is **never** reused across scopes, so the count is bounded by work in flight rather than by uptime. `ManagerAPI.scope()` exposes it and `Library/Web/App.py` opens one per **POST** request (callbacks; GETs are static assets and would pay a connection for nothing). Consumers call `attach()`, never the constructor — with no scope active it is exactly a fresh `with`. Measured: a Scheduler render 154 → 38 ms, 4 connections → 1. **Connection sharing:** a clone that differs from its origin only in schema/table borrows the origin's live connection instead of dialing its own — schema and table are query scope, not connection parameters, since every statement is fully qualified through `_target_`. `_link_` (host · port · user · password · admin · database · autocommit) decides; borrowing is refused for admin, a different database, a disconnected origin, and **any non-autocommit connection**, so transaction semantics are untouched. Measured 2.7× on a Scheduler page render (336.6 → 125.0 ms), 2 physical connections per call → 1. A borrower closes its cursor, never the connection.
- **`Library/Engine`**: Generic multi-state-machine engine (`EngineAPI`, `MachineAPI`, `StateAPI`, `TransitionAPI`). Zero trading domain knowledge.
- **`Library/Formulas`**: Financial and utility formulas (`DateTime`, `Spot`, `Historical`).
- **`Library/Indicator`**: Trading indicators in `Technical`, `Fundamental` (incl. the Forex Factory `Calendar` scraper), `Sentimental` subpackages, plus the umbrella `IndicatorAPI`.
- **`Library/Logging`**: The framework logger — 7 modules, API-surface docstrings. `Level.py` (`VerboseLevel`, ordered by **verbosity** not severity, so `Debug` = 6 is the largest; values mirrored to C# by `Setup/Enum.py` — never renumber). `Logger.py` (`LoggerAPI` abstract sink + the cached-second `stamp()`; class-level `Gate` = most verbose enabled level lets a suppressed record return after one integer compare, `Targets[level]` precomputes the accepting sinks so per-sink filtering is off the hot path; `write()` never raises, falling back to `sys.__stderr__`). `Console.py` (`ConsoleAPI` — colors the level only, and only when `isatty()`; enables VT on Windows; resolves `sys.stdout` per write so capture/redirection works). `File.py` (`FileAPI` — **`tempfile.gettempdir()/Logs/<entry-point>.log`** by default, `set_path()` to persist; `program.log` + `.1`/`.2` rotation, age-based retention pruned on open; append mode, UTF-8, `newline="\n"`). `Storage.py` (`StorageAPI` — durable DB sink, **one row per log not per record**: bounded queue + background writer so callers never block, level **hard-capped at `Warning`**, content flushed on a cadence with a size cap; re-entrancy guard stops `Library/Database`'s own logging from recursing). `Logging.py` (`LoggingAPI` — the façade, a real `logging.Logger` subclass; sinks are shared class attributes so `log.console`/`log.file`/`log.storage` configure the whole process; lambda content is built only if a sink accepts it; `Class`/`Subclass` default instance tags auto-derived from the caller; `with log:` locks configuration so the outermost entry point wins; `@log.guard`; `LoggingAPI.install()` attaches `BridgeAPI` to the stdlib root and chains `sys`/`threading` excepthooks so third-party records and uncaught crashes land in the sinks). Durable rows live in the Postgres **`Logging`** schema via `Log.py` (`LogAPI`), which `Scheduler.Run.LID` references `ON DELETE SET NULL` — pruning log content keeps run history intact.
- **`Library/Market`**: Market data structures (`MarketAPI`, `BarAPI`, `TickAPI`, `PriceAPI`, `SeriesAPI`, `TimestampAPI`).
- **`Library/Model`**: AI/ML components — `Core/` (`AgentAPI`, `NetworkAPI`, `MemoryAPI`, `Noise`) and `Method/` (`DDPG`, `SAC`, `TD3`), plus `Split.py` (walk-forward splitter).
- **`Library/Portfolio`**: Trading portfolio entities (`PortfolioAPI`, `AccountAPI`, `OrderAPI`, `PositionAPI`, `TradeAPI`, `SessionAPI`, `PnLAPI`). `Sizing.py` and `Statistic.py` are **function modules, not classes** — Sizing exports `SizingMode` plus the `calculate_*_volume` family (normalized · fixed amount · fixed fractional · Kelly · volatility target · risk parity); Statistic keeps only what is genuinely Portfolio-coupled — the Polars views, the five schema dicts (`Metrics`/`OrderView`/`PositionView`/`TradeView`/`DealView`) and the report generators. Everything context-free moved to `Library/Statistic` on 2026-09-04.
- **`Library/Protocol`**: Wire protocol shared with the C# Connector — `Action/` (commands) and `Update/` (events); `ActionID`/`UpdateID` enumerations.
- **`Library/Spotware`**: Spotware/cTrader API helpers; research/integration scratchpad.
- **`Library/Statistic`**: Context-free trading analysis — a foundation layer beside `Utility`, importing nothing from Market, Portfolio, App or System. Extracted from `Portfolio/Statistic.py` and the App spec layer on 2026-09-04, because statistics are not a portfolio concern. `Label.py` (118 metric-name constants — the one module the codebase may star-import, since it is nothing but constants) · `Metric.py` (30 pure calculations: returns · volatility · Sharpe/Sortino/Calmar/Sterling · ratios) · `Series.py` (`underwater` · `overwater` · `periodic` · `rolling` · `covariant` · `distribution`) · `Payload.py` (11 readers over a stored plot payload — `tabulate` · `transpose` · `trace` · `diurnal` · `stitch` · `tick` · `ordinal` · `grouped` · `searched` · `winners`) · `Workspace.py` (the Dash-free chart/table spec dataclasses) · `Composition.py` (13 view compositions, including `backtest` and `compare`). **A hardcoded metric label is a drift bug** — `System.py` writes `tables[BENCHMARK_LABEL]` and `Composition.py` reads `transpose(payload, BENCHMARK_LABEL)`; 134 literal label strings across 11 files were replaced by these constants.
- **`Library/Strategy`**: Strategy framework (`StrategyAPI`, `StrategyType` — `Download` 1, `NNFX` 2, `DDPG` 3, `Trend` 4 — values mirrored to C# by `Setup/Enum.py`). The constructor takes all seven `Parameter` sections in canonical order (money · risk · signal · technical · fundamental · sentimental · portfolio), each stored as `self.*Management`. Layers: `Model/` = generic RL building blocks (`Reward`, `Action`, `Normalizer`, `Observation`); `Rule/` = `Download`, `NNFXStrategyAPI` (money/risk base — stagnation stop, drawdown scaling, SO/TSL machine, `SizingMode` ∈ {`Volume`, `Balance`, `Risk`}) and `TrendStrategyAPI` (adds the indicator signal machine); `Hybrid/DDPG.py` = `DDPGStrategyAPI` (**a sibling of NNFX, not a subclass** — it owns its own sizing via `Model/Action.py` and uses only `RiskPercentage`/`ATRScale`, so it deliberately has none of the NNFX stop/scaling machinery; `ActorRegularization` 0 = DDPG, >0 = RDDPG) with its own normalizer/observation. Agents themselves live in `Library/Model`. **Parameters resolve through `Ladder.py`, not a folder tree.** Each strategy carries `Defaults` in its class body keyed by system kind (Realtime and Backtesting are equivalent and share one entry), and `LadderAPI` merges overrides key by key up global → provider → category → ticker → timeframe — most specific wins, anything undefined falls through, and a missing override is **not** an error. Overrides live in the persisted tier (`inspect_persistent("Overrides")`), are written by `promote()` as sparse deltas stamped with the run that produced them, and are read back by `provenance()`. This retired the 66-file `Library/Parameter` tree, which carried only **11 distinct configurations** — Download and Trend each had exactly one across 52 and 32 files.
- **`Auto` only resolves an indicator's declared ladder.** In an Optimization space, `Auto` reads `SlotAPI.ladder` off the technical indicator named in the **leading** slot, so it is meaningful only from slot 2 onward (`SMA · Auto` → 20 windows · `SMA|EMA · Auto` → 40). It has no meaning on a scalar such as `RiskPercentage` — there is no ladder to read — which is why those parameters carry lists or ranges and not `Auto`. `expand_parameter` **refuses** an `Auto` it cannot resolve, naming the parameter (`MoneyManagement.RiskPercentage`); it used to fall through and silently pass the *string* `"Auto"` in as the parameter value. Preferring `Auto` where a ladder exists is not cosmetic: the ladder supplies the coarse-to-fine levels, so Trend went from 1 round to 3 (192 → 640 candidates) purely by switching `Baseline`'s window to `Auto`.
- **`Library/System`**: Python Trading Engine (`SystemAPI`, `SystemType`, `LifecycleAPI`, `RealtimeAPI`, `BacktestingAPI` + `DatasetAPI` tape, `LearningAPI` DRL trainer). `Main.py` is the CLI entry point. `OptimizationAPI` is a **sibling of `LearningAPI`** — both orchestrate N backtests over `SplitAPI.walk_forward_folds` staging and share `_dispatch_()` (the worker payload) and `_resolve_()` (the worker-side security rebuild) on `BacktestingAPI`. It expands a `Optimization.yml` space into a candidate grid, sweeps each fold serially or across a `ProcessPoolExecutor`, selects by `FitnessType` under `SelectionMode` (`Argmax` · `Plateau`, the latter bucketed by hash rather than an O(n²) pairwise scan), elects the most-selected candidate across folds and runs it once more over the held-out test window (or the full range). **Artifact policy is uniform across both orchestrators:** candidates and seeds write nothing — only the elected/full-range run emits, and only for the flags the user passed. Two shared `SystemAPI` context managers enforce it: `deliverables(report, export, plot)` scopes the three flags to that one run, and `quieted(level)` drops both sinks to `Warning` for every non-delivering pass so a 1000-candidate sweep does not flood the log while errors and exceptions stay visible. **Output flags take an optional path** — `--export`/`--plot`/`--profile` bare write to `%TEMP%/Exports`, `/Plots`, `/Profiles`, and with a value persist there instead (`inspect_destination`); `--report` prints tables to the terminal.
- **`Library/Scheduler`**: DB-backed job orchestration on the Postgres `Scheduler` schema; replaces Windows Task Scheduler with a single boot daemon. **Model:** one shared `Kind` enum ∈ {`Manual`, `Scheduled`, `Service`} spans the module — on a Workflow it is the lifecycle (`Manual` = run on demand, no cron · `Scheduled` = cron opens cycles, `Schedule` required · `Service` = one **resident** cycle, only `Service` members allowed), on a Task the execution style (`Manual` standalone on-demand · `Scheduled` run-to-completion · `Service` always-on), on a Cycle/Run **how that execution was triggered** (daemon = `Scheduled`, human = `Manual`, supervision = `Service`). `WorkflowAPI` (`Waits` default true governs overruns) → `CycleAPI` (**one execution of a workflow** — the Airflow-DagRun analog: `Kind` · `Status` · `StartedAt`/`StoppedAt`; opened by the workflow cron at its logical instant, by `run_workflow`, or by boot) → `TaskAPI` (`Type` ∈ {`Batch`, `Shell`, `Python`} · `Kind` · optional `RequiresApproval`/`RequiresReview` gates · `MaxRetry`/`RetryDelay` · `Waits` (default true)/`Tolerates` (default true)) → `RunAPI` (audit record: kind, status, exit code, 0-based `Retry`, duration, peak memory, `PID`, `Auditor`, captured log; per-run `MachineAPI`; status groups `Busy` ⊂ `Live` ⊂ `Active` — `Busy` = Waiting·Running (a process holds a heartbeat: budget, reaper) · `Live` = +Retrying (work in motion: cancellable, pauses services) · `Active` = +Approving·Reviewing (unfinished: blocks the DAG, dedups, keeps the cycle open)); `DependencyAPI` holds the DAG edges, cycle-checked and evaluated by `CoordinatorAPI` (networkx). **Semantics:** ONLY the workflow `Schedule` (or a manual run) opens a Cycle; a member task's `Schedule` is an **earliest-start gate inside the cycle** (never a trigger; `Manual` cycles ignore gates); a member fires when its gate time passed AND its dependency rule holds — `Waits=true` waits for predecessors (`Tolerates=true` accepts any terminal outcome · `false` demands `Success`), `Waits=false` fires at its gate time (blocked only by an already-`Failure` predecessor when `Tolerates=false`). `ManagerAPI` **validates coherence** — Kind vs Schedule, Service-workflow purity, and member schedules fitting inside every workflow period (`CoordinatorAPI.fits`). The cycle stays open while members are active, dispatchable, or gated in the future; it closes `Success`/`Failure` and mirrors member gates as `Approving`/`Reviewing`. **Overrun:** the next cron occurrence waits for the open cycle when `Workflow.Waits` (default) · `Waits=false` **resets** — kills the open cycle's live runs (`Failure`) and opens fresh. **Overrides (all stamp `Run.Kind=Manual` + `Auditor`):** `run_task` early-starts a member into the open cycle ignoring its gate; `skip` inserts a synthetic run without executing; `cancel` tree-kills a live run via its `PID` — skip and cancel **simulate a termination with a chosen result** (default Success · `--failure`) that flows through the gates (`RequiresApproval` → `Approving`, `RequiresReview` → `Reviewing`). Approval gates a passing run and Review gates a crashed one (Accept → `Success`, Reject → `Failure`; gates block downstream); crashes retry up to `MaxRetry` with latest-attempt-governs; a heartbeat lease lets the reaper recover dead runners/reboots; `Service` tasks are supervised always-on, suspended while a workflow-mate `Scheduled` run is **executing** (`Waiting`/`Running`/`Retrying` — a gate-parked `Approving`/`Reviewing` run does not hold services down), respawned no sooner than `RetryDelay`, and halted after `MaxRetry` consecutive short-lived crashes (**0 = respawn forever, the service default**, systemd-style). **A suspension is not a failure and the daemon says so itself:** `_service_` closes the run `Success` stamped `Suspend` the moment it terminates a service for maintenance. Leaving it to the reaper was wrong — the daemon hard-kills the Runner, so no exit code is ever written and the stale heartbeat was reaped as `Failure`. That is why `Environment.Tunnel` showed 29 straight failures while the tunnel was healthy: the daily `0 4 * * *` cycle pauses services for `Cache`/`Retention`/`Update`/`Version` and every suspension was recorded as a crash. Only a termination the daemon **initiated** is closed this way; a service that dies on its own is still left to the reaper. `Run.PID` records the run's root Runner process — the tree that `cancel` and reset kill. **Boot sequence:** at daemon start every enabled service-bearing workflow is boot-launched as a fresh maintenance run, and a down `Service` only spawns once its DAG predecessors are satisfied (`Scheduled` predecessor = a run finished since this daemon start · `Service` predecessor = alive process) — so a reboot replays `Update → Tunnel → Server` strictly in order. **Processes:** `SchedulerAPI` is event-driven — Postgres `LISTEN/NOTIFY` triggers (created by `Setup/Scheduler.py`: any Workflow/Task/Dependency change · Run inserts/deletes · Run **status** changes only, so heartbeats stay silent) wake the daemon instantly, with the `interval` (30s default; `interval`/`concurrency` constructor params — zero environment variables) as the cron/fallback cadence; it spawns one `Runner` process per run (never threads, `CREATE_NO_WINDOW` so tasks never open consoles); `ExecutorAPI` executes the artifact (psutil peak-RSS sampling, heartbeats, per-run log file under the system temp `%TEMP%/Quant/Runs`). **Surfaces:** the four Scheduler surfaces (Workflows · Tasks · Runs list pages plus the Tasks/Cycles/Runs sub-grids on the detail pages) all run on `TableAPI`, with only the workflow DAG left in Plotly. Both entity forms are declared as a `FieldAPI` tuple and share `_form_`/`_blank_`/`_populate_`/`_submit_` (validation · dispatch by `_entity_` · notification); `_pairs_` renders the same declaration as the read-only detail view and `_intervene_` is the one outcome-bearing sweep behind Skip and Cancel. `ManagerAPI` opens a connection per call (`with PostgresDatabaseAPI(...)`) and that is deliberate — a thread-local connection cache was tried and **reverted**: keyed to transient waitress threads with no ceiling and no return, it grew to 409 clients against `max_connections` 400. A cache is not a pool. What replaced it is connection *sharing* inside a block (see `Library/Database`), which halves the cost while strictly reducing the connection count; a bounded pool across blocks remains unbuilt. `ManagerAPI` is the single mutation authority shared by the Python console, the CLI (`python -m Library.Scheduler.Main <workflow|task|cycle|run|serve> <action>`), and the web UI; push wake-ups ride the generic `DatabaseAPI.listen`/`notify`/`wait` seam (native on Postgres, sleep-degraded elsewhere); `Serve.py` is the headless boot entry; `Tray.py` wraps it as the silent system-tray app named `Scheduler` (Open in Terminal — Windows Terminal live-tail of `Logs/Scheduler.log` · Verbose Logging toggle · Launch/Shutdown in-process · Restart relaunches the boot script so code changes apply · Quit, headless fallback) — it knows nothing about the web app (`Library/Web` has its own `Quant Cognition` tray; the only sanctioned coupling is the web Scheduler page consuming `ManagerAPI` like the CLI does). Libraries: `croniter` · `psutil` · `networkx` · stdlib `subprocess`.

### Search and analysis design (delivered 2026-08-25)

- **One journal, many projections.** Each engine records **one row per evaluation** rather than four accumulators — Optimization `{Fold, Stage, Round, Candidate, Parameters, Fitness, Elected}`, Learning `{Fold, Seed, Episode, Train, Validation, Elected}`. Every table and pane is a projection of that single journal, so a new flag combination needs no new plumbing.
- **A workspace per system, composed not forked.** `SystemAPI._workspace_()` is the hook: `BacktestingAPI` returns `Workspace.backtest(...)` unchanged, `OptimizationAPI`/`LearningAPI` return `Workspace.optimization(...)`/`.learning(...)`, which call `backtest(...)` for the elected run and **add** panes and sheets. CLI and UI parity is structural, not maintained — both read `Result.json`. Flag dependence falls out of one rule: **a pane or sheet appears iff the run produced that dimension** (Candidates and Convergence always · Stages on a staged space · Rounds on any `Auto` or range slot · Folds/Walk-Forward/Generalization on `--training`/`--validation` · a held-out row on `--testing` · Episodes and Seeds for Learning).
- **The walk-forward curve is the honest one.** Each fold's model evaluated **only on its own out-of-sample window**, concatenated into one equity curve — no model ever sees its own validation data. Overlaying the elected model answers the deployment question: *is the one model I ship as good as the rolling refit implied?* In `compare`, each workspace declares a **headline** series — equity growth for Backtesting, the stitched curve for Optimization and Learning when folds exist — and because like-for-like is not always possible the comparison sheet carries a **System** row naming what each column actually is.
- **`PaneAPI.scale` exists because Lightweight's time scale is date-based.** Convergence and episode charts are ordinal, and `Lightweight.js` keeps one flat `charts` list syncing every pane by visible logical range, so an ordinal pane would scroll in lockstep with the price panes. Panes group by scale: range and crosshair sync happen **within a group**, the date brush drives only the `time` group, and `index` panes install a `tickMarkFormatter` rendering the ordinal. Four renderer defects, all found by opening a browser rather than trusting the payload: ordinal stamps reaching `WorkspaceAPI.timeline()` started the axis at **1970**; the hidden **backbone series** that aligns panes gave ordinal charts ~800 phantom bars, making `fitContent()` a no-op (ordinal panes now build a backbone from their own stamps); with `timeVisible: false` the scale buckets by **day**, so times 1·2·3 seconds collapsed onto one bar (ordinal points are now a day apart); and 14 panes sharing one fixed-height column squashed to ~30px (panes now have a 168px floor and the column scrolls).

### Setup (`Setup/`)
- **One boot entry.** Windows Task Scheduler runs only the master orchestrator (`Quant Scheduler` logon task → `pythonw Script/Scheduler.py` → silent tray daemon). The daemon boot-launches the service-bearing workflows (a logon replays `Environment.Cache → Retention → Update → Tunnel → Server` in order), supervises services, cron-launches scheduled workflows, and advances manual ones.
- **Three standard workflows** (registered by `Setup/Install.py`, owned by the real administrator `Setup.Auth.ADMIN`): **`Setup`** (manual) = the FK-ordered provisioning DAG (`Enums` · `Auth`→`Logging`→`Scheduler` · `Universe`→`Market`/`Portfolio` · `Indicator`, all `Tolerates=false` — provisioning is zero-tolerance; `Logging` precedes `Scheduler` because `Run.LID` references `Logging.Log`); **`Environment`** (daily `0 4 * * *`) = `Environment.Cache` (bytecode/tooling/build cache cleanup) → `Environment.Retention` (prunes expired log files from the temp folders and expired `Logging.Log` rows) → `Environment.Update` (conda env refresh — suspends the services) → `Environment.Tunnel` (cloudflared, `Service`) → `Environment.Server` (waitress app, `Service`); **`Market`** (daily `0 6 * * *`) = `Market.Calendar` (Forex Factory economic calendar), extensible.
- **Provisioning tasks** are idempotent Python modules with a uniform `main(database="Quant") -> int` and RULES logging — re-run any task or the whole DAG safely; each also runs standalone (`python -m Setup.Auth`, …).
- **Shared task plumbing lives in `Setup/Task.py`** - `migrate(db, *datapoints)` (the `migrate=True, autosave=False, autoload=False` incantation, 23 repetitions across 7 files) and `provision(log, name, work, *, database, detail)` (the connection + try/except + exit-code wrapper that 7 mains spelled out identically). **`provision` takes the logger as its first argument and never builds one** - logger identity resolves from the calling frame, so constructing it inside `Task.py` renders every provisioning line `Task - Setup` instead of `Market - Setup` and silently destroys per-task attribution. `Auth`, `Scheduler` and `Indicator` keep bespoke `main()`s (admin seeding after the connection closes · two setup calls · `start`/`stop` arguments) and use only `migrate`.
- **The enum block providers declare, they do not run.** `Action` · `Position` · `Strategy` · `Stream` · `System` · `Update` are five-line modules exporting one `*_block()` each, and `enum_block(name, enumeration)` takes the enumeration itself rather than a pre-built member list. `python -m Setup.Enum` is the single entry point - the four duplicate `__main__` blocks that each regenerated the whole file are gone. Guard any change to the generator with the output hash: the committed `Enum.cs` is `8376276ae3a71fbe` (sha256, first 16).
- **Entry point:** `python -m Setup.Install [--database] [--boot]` provisions everything in-process, registers the three workflows, and with `--boot` creates the Windows logon task. `Scripts/` holds only the essentials: the boot launcher (`Scheduler.py`) plus the environment helpers (`System`/`Conda`/`UV` updaters and the `Cache` cleanup each updater runs first).
